# Internal security review of the v0.2 diff, September 2026

Adversarial review of everything v0.2 added or moved — `git diff v0.1.0..HEAD`, 169 commits — against the threat model ([ADR-0029](../adr/0029-threat-model.md)) and the per-phase threat models in [ADR-0082](../adr/0082-routes-guards-and-middleware.md), [ADR-0083](../adr/0083-modules-stack-migrations-and-ejection.md), [ADR-0085](../adr/0085-security-layers.md), [ADR-0086](../adr/0086-dev-portal-tunnel.md) and [ADR-0087](../adr/0087-testing-sign-in-from-the-dev-portal.md). Roadmap item 105. Reviewed on 2026-09-17 on branch `framework/phase-12-12a`.

This follows the [v0.1 internal review](2026-09-internal-review.md), whose 43 findings are all fixed; it does not repeat that work. It covers the new and moved code only.

**Result: 17 findings — 1 High, 6 Medium, 6 Low, 4 Info.** Ten are fixed, each with a regression test that fails without its fix; seven are left to the maintainer with a written reason, because each needs a design decision, an API addition or a change to frozen v0.1.0 behaviour rather than a review patch. No cross-tenant data access, no MFA bypass in the shipped wiring, no SQL injection, no secret in a committed file.

Separately, **ten of the phase threat models' "tested" claims are not backed by a test that exercises the hostile case**, and seven more are backed only weakly. The list is in [Phase threat-model claims](#phase-threat-model-claims). One of them — ADR-0083 Phase 4's claim that `Customize` can't change a route's middleware — was not merely untested but false; it is finding GUARD-1.

Like the v0.1 review, this was done by the project, not by an independent party. `v1.0.0` still waits for the external review.

How it was done:

1. **Read the code, not the docs.** For each area: what must be true, how the code enforces it, and what a hostile client, a hostile app developer (hooks, custom guards, `Customize`, ejected code) or a hostile provider or webhook sender could do. Five parallel area reads and a separate audit of the ADRs' claims fed a single triage; every finding below was then re-derived and reproduced by the lead before it was written down. Three reported issues did not survive that step and are listed under [Reported and not confirmed](#reported-and-not-confirmed).
2. **Proof before fix.** Every confirmed finding got a test that fails against the code as it was and passes after the fix. Each fix was reverted once to watch its test fail; the command and its output are in the finding.
3. **Claims audit.** Every "tested" claim in the five phase ADRs was traced to the test that is supposed to back it, and the test read to see whether it exercises the attack or only the happy path.
4. **Static passes.** `golangci-lint` (with gosec) over the root module, `gorbital`, `cli`, `httpx` and every module; `govulncheck` v1.8.0 over each module; `gitleaks` v8.30.1; and greps for tokens, passwords, keys and email addresses in logs, errors and responses (ADR-0007).

Severity, as in the v0.1 review: **High**, an account or a secret can be taken, or a stated security control does not hold, without special access; **Medium**, a control can be bypassed or abused, or a documented guarantee is false; **Low**, a weakness that needs an unusual position or has limited impact; **Info**, hardening or a documentation gap.

## Findings

### Routes and guards

| ID | Severity | Title | Status |
|---|---|---|---|
| GUARD-1 | Medium | `Customize` could replace a route's sign-in check and guards, leaving the OpenAPI document saying the route was protected | Fixed |
| GUARD-2 | Info | Nothing pins the set of public routes, so a route becoming public is silent | Maintainer |

#### GUARD-1 — `Customize` could remove deny by default

`gorbital.Customize` gives an app the Huma operation "as the other options, guards and deny by default have built it", and its doc promises: *"fn can't change the method, path, operation ID, security requirements or operation middleware: registration fails when it does, so a route can't leave deny by default or its guards behind."* ADR-0083 Phase 4 repeats the claim in its threat model.

The check compared only the **length** of the middleware slice (`gorbital/router.go:267,274` before the fix):

```go
method, path, id, security, middlewares := op.Method, op.Path, op.OperationID, fmt.Sprint(op.Security), len(op.Middlewares)
…
if op.Method != method || … || len(op.Middlewares) != middlewares {
```

The sign-in check (`requireActor`) and each guard are entries in that slice. Replacing it with entries of the same length passes:

```go
gorbital.Get(r, "/v1/secret", handler, gorbital.Customize(func(_ huma.API, op *huma.Operation) {
    op.Middlewares = huma.Middlewares{func(hctx huma.Context, next func(huma.Context)) { next(hctx) }}
}))
```

**Exploit path.** The route keeps `op.Security = openapi.Bearer` and its `x-gorbital-guards` extension, so the OpenAPI document, the contract tests that read it and a human reviewer all still say the route needs sign-in — and an anonymous request gets 200. The same trick removes `guard.Permission`, `guard.OrgMember` or a rate limit. It needs app code, so it is a hostile-or-careless app developer, not a hostile client; but `op.Middlewares = huma.Middlewares{mine}` on a route with exactly one guard is an easy accident, and this is the one documented escape hatch a reviewer is told cannot strip a route's protection. Ejected and generated code uses `Customize`.

**Fix.** The chain is compared entry by entry, by each function's code pointer (`gorbital/router.go:263-297`, `sameMiddlewares`). The entries are built by unexported functions of the package (`adapt`, `requireActor`, `registry.guardMiddleware`), so nothing outside it can produce a function with one of their code pointers and put it back.

**Test.** `TestCustomizeCantReplaceGuards` (`gorbital/gorbital_test.go`) covers four shapes — replacing the sign-in check, replacing a guard, replacing one entry of the chain, reordering the chain — and fails the test when registration succeeds, printing the status an anonymous request got. `TestCustomizeKeepsWorkingOnTheOperation` checks that what `Customize` exists for (here `MaxBodyBytes`) still works.

```
$ go test -run TestCustomize ./...          # with len() restored
--- FAIL: TestCustomizeCantReplaceGuards/the_sign-in_check
    Mount() = nil; the route was registered and an anonymous POST answered 200 ""
--- FAIL: TestCustomizeCantReplaceGuards/a_guard
    Mount() = nil; the route was registered and an anonymous POST answered 200 ""
```

#### GUARD-2 — no test pins the set of public routes (maintainer)

Deny by default makes a route public only through `guard.Public()`, or through `operation.Register` with an operation that has no `Security` — which is how a v0.1 operation that never had one is carried over, and is correct, since Huma never enforced `Security` in v0.1. Both are visible in the OpenAPI document as `x-gorbital-guards: ["public"]`.

Nothing asserts the **set**. `gorbital/internal/contract/contract_test.go:124` and `gorbital/internal/integration/contract_test.go:109` require the extension to exist and then `delete` it before comparing with the frozen v0.1.0 documents. So a change that makes a route public — a mistaken `guard.Public()`, an `operation.Register` for an operation whose `Security` was dropped in a refactor, an ejected module's edit — passes every test in the repository.

**Not fixed.** A golden list is cheap to add but belongs with the maintainer's decision about where it lives (the full app's contract test, or an `orb doctor` check that an app can run on itself, which would also cover generated apps). Recommended: assert the exact set of `["public"]` operations in `gorbital/internal/integration` and in each golden app, so adding one is a deliberate edit to a list.

### Sign-in

The move of sign-in into `gorbital/authhttp` is the largest part of the diff, and it holds up. The ordering that matters is right and tested: a banned account is refused before `BeforeLogin` runs and again before the session row is written (`gorbital/authhttp/internal/usecase/login.go:190,211`); `SignIn` for a module's own method applies the same login rate limits, the unverified-address refusal, the second-factor challenge, the ban and the hooks as a password sign-in (`.../usecase/sign_in.go`); `Login` verifies a dummy hash on every enumeration branch, including "account without a password", and checks the rate limit before the account lookup, so the branch taken doesn't depend on whether the address exists.

Hook refusals cannot impersonate a built-in code: `Refuse` panics at package initialisation on a reserved code, and `hookFailed` re-checks, so a `&Refusal{}` built by hand with a reserved code becomes a 500 rather than a forged `invalid_credentials` (`gorbital/authhttp/hooks.go:128-148,231-243`). Hooks fail closed — any error other than a valid refusal is a `HookError`, and registration rolls the account back. `AuthenticateAfterInput` cannot be set on a public route or a route with guards; registration fails (`gorbital/router.go:211`), and it never removes the check, only moves it after input validation, which `TestSignedInRoutesRefuseAnonymous` exercises across every `/v1/auth/` and `/ops/` operation the document marks as needing sign-in.

| ID | Severity | Title | Status |
|---|---|---|---|
| AUTH-1 | Info | `AfterLogin` hooks that ignore their context outlive the 5 s budget; registration's 300 ms padding hides only fast hooks | Maintainer (known, documented) |

#### AUTH-1 — the `AfterLogin` budget bounds the wait, not the work (maintainer)

`runAfterLogin` (`gorbital/authhttp/hooks.go:246-273`) runs the hooks on their own goroutine with a 5 s context and returns when they finish *or* the deadline passes. Go cannot stop a goroutine, so a hook that ignores its context keeps running after the response is sent; the warning line says as much. Likewise, `OnRegister` and `RegisterFields` run inside the request, and the 300 ms floor that hides account existence (v0.1's AUTH-S-4) only hides hooks that finish inside it: a hook that is slower for an address that has no account reopens the timing channel the floor was added to close.

**Not fixed.** Both are properties of running app code in the request, which is what hooks are for; the alternatives (a job queue for `AfterLogin`, equal work on both registration branches) were weighed and rejected in the v0.1 review and ADR-0083 Phase 6 for reasons that still hold. This is a documentation matter: the hooks guide should say plainly that an `AfterLogin` hook must honour its context, and that an `OnRegister` hook slower than 300 ms can reveal whether an address has an account.

#### HTTP-1 — IPv4-mapped trusted-proxy ranges

Two defects in one function (`httpx/trusted_proxies.go:19-40` before the fix). `ParseTrustedProxies` never unmapped its entries, while `remoteAddr` and the `X-Forwarded-For` hop walk always unmap the address they test, and `netip.Prefix.Contains` is false across families.

- `::ffff:10.0.0.5` was stored as `::ffff:10.0.0.5/128` and `::ffff:10.0.0.0/104` stayed 4-in-6. Neither matched **anything** — not an IPv4 peer, not even a mapped peer. An operator's `APP_TRUSTED_PROXIES` silently trusted nobody, `X-Forwarded-For` was ignored, and every client's address collapsed to the proxy's in logs, audit rows, per-IP rate limits and `OPS_ALLOWED_IPS`. It fails closed, but it defeats the operator's intent without a word.
- Sharper: a mapped range **shorter than /96** was silently re-based, not refused. `netip` masks `::ffff:10.0.0.0/8` to `::/8` — a real, non-empty IPv6 prefix that is neither what the operator wrote nor caught by `ErrTrustAll`, which only tested `Bits() == 0`. It trusts `::1`, `::` and every IPv4-compatible `::a.b.c.d` form. Reproduced: with that entry, a request whose peer is `[::1]:80` and whose `X-Forwarded-For` is `198.51.100.1` had its `RemoteAddr` rewritten to `198.51.100.1:0`.

`httpx/ipfilter` does **not** have this gap: `canonicalPrefix` (`httpx/ipfilter/ipfilter.go:64-75`) unmaps at /96 or longer and refuses shorter mapped ranges, and its fuzz targets assert the canonical form.

**Fix.** The same canonicalisation, as `canonicalProxy`: mapped entries are read as the IPv4 range they name, ones shorter than /96 are refused, and `ErrTrustAll` is tested **after** unmapping, so `::ffff:0.0.0.0/96` is refused like `0.0.0.0/0`. Zoned single addresses are refused, as in `ipfilter`. `TrustedProxies` applies the same canonicalisation to prefixes passed straight in and drops what it cannot canonicalise, so a family-mixing range trusts nothing instead of `::/8`; its doc now points callers at `ParseTrustedProxies`, which reports these as errors.

**Test.** `TestParseTrustedProxiesMappedEntries` and `TestTrustedProxiesDropsRangesItCantUse` (`httpx/trusted_proxies_test.go`), including the end-to-end case that a mapped entry trusts its proxy whether the peer arrives as IPv4 or IPv4-mapped.

#### HTTP-2 — `Unwrap` before the deadline escaped the lock

`httpx/timeout` serialises the handler's writes with the 503 that another goroutine writes at the deadline. Every method took the mutex — except that `Unwrap` answered from the timeout state **at the moment it was called** and returned the bare `tw.w` when the deadline had not yet passed (`httpx/timeout/timeout.go:290-297` before the fix). Its doc promised "after a timeout it returns a writer that discards everything", which only held if `Unwrap` was called after the timeout; `TestTimeoutResponseControllerAfterTimeout` tested only that safe direction.

**Exploit path.** A handler (or wrapping middleware — `httpx.Capture` embeds a writer exactly this way) that unwraps early and writes later writes to the real `http.ResponseWriter` with no lock, concurrently with `answerLocked`. Reproduced under `-race` with a single-goroutine handler: races reported at `timeout.go:153` (`h.Set`), `:156` (`WriteHeader`) and `:157` (`Write`). The unsynchronised `http.Header` map write is the live risk — Go's `fatal error: concurrent map writes` is unrecoverable and kills the process, so a handler that can be made slow turns a timeout into a process-wide denial of service. On a recorder it also put the handler's headers and body onto the 503; on a real server `net/http` truncates past `Content-Length`, so this is not request smuggling.

**Fix.** `Unwrap` never hands out the underlying writer. It returns a `guardedWriter` that forwards `Header`, `Write`, `WriteHeader`, `FlushError`, `Flush`, `Hijack` and the three `ResponseController` methods back through `timeoutWriter`'s locked methods, so a writer kept across the deadline still stops at it. Interfaces the timeout writer does not forward, such as `http.Pusher`, are no longer reachable through `Unwrap`; that is stated in its doc. `http.ResponseController` already found flushing, hijacking and the deadlines directly on `timeoutWriter` and still does.

**Test.** `TestTimeoutUnwrapBeforeTheDeadline` (run with `-race`) unwraps first, writes after the deadline, and asserts no handler header or body reaches the 503; `TestTimeoutUnwrapReachesTheController` asserts the guarded writer still carries the controller.

```
$ go test -race -run TestTimeoutUnwrapBeforeTheDeadline ./httpx/timeout/   # before the fix
WARNING: DATA RACE   (×6)
```

#### HTTP-3 — Early Hints leaked the handler's headers onto the 503

`WriteHeader` with a 1xx status calls `copyHeaders()`, which clears the real header map and copies the handler's private one into it, without setting `started` (`httpx/timeout/timeout.go:202-206`). A later `answerLocked` then wrote the 503 into a map holding the handler's headers, so a response the handler never wrote carried them — reproduced with `X-Internal-Backend: db-primary-7` on the 503. The existing `TestTimeoutEarlyHints` checked only the body.

**Fix.** The timeout writer keeps `outer`, a clone of the header map as it was before the handler ran, and `answerLocked` restores it before setting the problem headers. The middleware around the timeout keeps its headers — the request ID, which `TestTimeoutWritesTheWholeResponse` asserts — and the handler's are dropped whether or not a 103 copied them.

**Test.** `TestTimeoutEarlyHintsHeadersDontReachThe503` (`httpx/timeout/timeout_test.go`).

#### JWT-1 — an app's HTTP client lost the JWKS redirect allowlist

`jwt.New` built its fetch client as `client := o.client; if client == nil { client = &http.Client{Timeout: fetchTimeout, CheckRedirect: checkRedirect} }`. The allowlist (https, or http on loopback, at most 3 hops) and the 10 s timeout applied **only** to the built-in client. `WithHTTPClient` is documented for "a proxy or custom root certificates", and the package's own examples pass a bare `&http.Client{Timeout: 5 * time.Second}` — which has `CheckRedirect == nil`, so Go's default applies: up to ten redirects, any scheme, any host.

**Exploit path.** The provider's JWKS endpoint (or anything that can inject a redirect into it — an open redirect on the IdP domain, a stale CDN rule, a compromised IdP tenant) answers `302 → http://attacker/jwks.json`. The attacker's keys are cached and every forged token verifies. Reproduced: with an app-supplied client, `New` followed a redirect to a plain-http, non-loopback host and failed only on DNS — `dial tcp: lookup attacker.example.com: no such host` — proving the request left the allowlist.

**Fix.** `keysClient` copies the caller's client and fills in `CheckRedirect` and `Timeout` only when they are unset, so an app that sets its own keeps it. The caller's client is not mutated.

**Test.** `TestAppClientKeepsTheRedirectPolicy` (both the default and an app's client) and `TestKeysClient` (`modules/jwt/jwt_test.go`).

#### JWT-2 — a provider claim could grant `ops.*`

The default actor mapping was `actor.Actor{Kind: KindUser, ID: c.Subject, Permissions: c.Strings(a.permissionsClaim)}`. `/ops` authorizes on the actor's permissions alone — `opshttp` says so itself ("Every operation needs an actor holding its `ops.*` permission") and does it with `actor.Require` (`gorbital/opshttp/internal/usecase/service.go:114-125`). Nothing filtered the claim.

**Exploit path.** In an app that wires `modules/jwt` as its authenticator and mounts `opshttp`, a token whose permissions claim contains `ops.settings.write` is a platform administrator: change runtime settings and flags, read the audit log, run jobs, browse and mutate file storage. Reproduced end to end through `Authenticator.Middleware`:

```
actor = {Kind:user ID:auth0|usr_1 Permissions:[ops.settings.write ops.audit.read books.book.read] StepUp:[]}
ESCALATION: an IdP claim granted ops.settings.write (StepUp=[])
```

Two things make this more than "the IdP is trusted". First, the claim often is not the operator's to set: `Config.PermissionsClaim` is documented as accepting `"scope"`, and an OAuth `scope` is asked for by the client; several providers map user-editable metadata into it. Second, `StepUp` is never populated for a JWT actor, so the permissions `authhttp` marks as needing a second factor are granted outright — the actor skips the step-up that the same permission requires for a session.

**Fix.** The default mapping drops permissions under `ReservedPermissionPrefix` (`"ops."`), the operations console's namespace. `Config.ActorFrom`, which an app writes deliberately, is untouched and is now documented as fully trusted, including that its `StepUp` is empty unless it fills it.

**Test.** `TestDefaultActorDropsOpsPermissions` (`modules/jwt/jwt_test.go`): the token is still accepted, its `ops.*` permissions are gone, `actor.Require` returns `ErrForbidden` for them, and the same claim through `ActorFrom` keeps them.

#### JWT-3 — no token-type check (maintainer)

`Verify` reads only `alg` and `kid` from the header (`modules/jwt/jwt.go:306-313`); `typ`, `at+jwt`, `token_use` and `azp` are never checked. ID-token-versus-access-token confusion is prevented only by the audience check — which does not separate them in the common configuration where `Audiences` is the OAuth client ID, as it is for Cognito, Firebase and Google ID tokens. Related: setting a non-default `AudienceClaim` leaves the registered `aud` claim entirely unchecked (`jwt.go:365-369`), so a token for another audience is accepted if the custom claim matches.

**Not fixed.** The right shape is a `Config.TokenType` (or a required-claims map) rather than a guess at each provider's conventions, and it is an API addition to an experimental package that the maintainer should design rather than have a reviewer bolt on. Until then the package doc should say that the audience check is the only separation between token types, and that a custom `AudienceClaim` replaces rather than adds to `aud`.

#### WEBHOOK-1 — replay inside the window, and repeated headers (maintainer, documented)

`webhook` and `guard.Webhook` have **no dedupe cache**: a captured request replays freely inside the ±5-minute tolerance, and with `TimestampHeader` unset there is no window at all. This is honestly documented in three places (`webhook/webhook.go:14-16`, `guard/webhook.go:56-59`, `HMACConfig.TimestampHeader`), and `mailevents` shows the pattern, keying `provider + ":" + webhook.ID` into a store with a 2× tolerance TTL. Separately, the header reads use `header.Get`, which takes only the first of repeated values, so a sender that splits signatures across repeated headers is refused unless the genuine one comes first — a fail-closed availability cost, never an authenticity one.

**Not fixed.** Dedupe needs a store and a TTL policy, which is an API decision (a `Seen` interface on `HMACConfig`), and the current split — library verifies, app dedupes — is deliberate. Recommended for v0.3: offer the dedupe store in the guard so the safe thing is the default, and switch the header reads to `Values()` + `Fields()`.

Everything else in the webhook path is sound and well tested: the timestamp is inside the signed content and bounded in both directions; `hmac.Equal` throughout, with **no `break`** in either loop, so every entry is compared with every secret and neither the matching secret nor the matching entry is distinguishable by timing; the delivery ID is rejected if empty, over 255 bytes, or containing `.` or whitespace, so `id.timestamp.body` cannot be re-partitioned; the body is bounded before hashing on both the declared and undeclared paths, and the exact bytes verified are the ones the handler receives; Svix's and GitHub's published vectors both verify.

#### OPS-1 — the ops address filter missed the strongest operations

`opshttp` installed the filter as a route group **on its own module router** (`gorbital/opshttp/module.go:92-98` before the fix):

```go
if allowed := platform.Config.OpsAllowedIPs; len(allowed) > 0 {
    filter, err := ipfilter.New(allowed, nil)
    …
    r = r.Group("", gorbital.Use(filter))
}
```

`r` is `opshttp`'s router, so the filter reached its own routes and nothing else. `/ops/` is not one module's: `authhttp` registers `/ops/auth/users` and `/ops/service-accounts` on its own router (`gorbital/authhttp/internal/delivery/ops_users.go:154-226`, `apikeys.go:180-217`).

**Exploit path.** An operator sets `OPS_ALLOWED_IPS` to their office range and believes `/ops` is network-restricted. An attacker holding a stolen `platform_admin` session or API key, from any address, gets 403 on `/ops/settings` — and 200 on the 24 operations outside the fence, which are the strongest the console has. Reproduced against a full app with `OPS_ALLOWED_IPS=10.0.0.0/8` from `198.51.100.7`:

```
24 /ops/ operations answered a client outside OPS_ALLOWED_IPS:
  POST   /ops/auth/users/{id}/roles         -> Unprocessable Entity validation_failed
  POST   /ops/auth/users/{id}/ban           -> Unauthorized unauthenticated
  POST   /ops/auth/users/{id}/impersonate   -> Unauthorized unauthenticated
  DELETE /ops/auth/users/{id}/sessions      -> Unauthorized unauthenticated
  POST   /ops/service-accounts/{id}/keys    -> Unprocessable Entity validation_failed
  … 19 more
```

(The 401 and 422 show the request passed the filter and reached the route's own checks; with the filter it is 403 `ip_not_allowed` for all 24.)

Aggravating: an app with `authhttp` and without `opshttp` served `/ops/auth/users…` with `OPS_ALLOWED_IPS` set and **no filter anywhere** — the value was parsed at startup and then silently unused. The documented contract was the opposite: ADR-0085 says `opshttp` puts *each* `/ops/` route behind the filter, and the module doc promises 403 `ip_not_allowed` for other addresses.

**Fix.** The filter is a property of the app, not of a module. `gorbital.New` applies it inside the middleware stack, around the mux, for requests under `/ops/` (`gorbital/app.go`, `App.opsAllowed`), so it covers every module's `/ops/` routes — including an app's own — and a custom `WithStack` cannot leave it out. It still matches the address `httpx.TrustedProxies` resolved, and still refuses before the route's sign-in check. The module-level group is gone. If the filter cannot be built (it cannot: `LoadConfig` builds the same one), `/ops/` is closed rather than served unfiltered.

**Test.** `TestOpsAllowedIPsCoversEveryOpsRoute` (`gorbital/internal/integration/allowed_ips_test.go`) reads the app's OpenAPI document, requires at least 60 `/ops/` operations, and asserts every one answers 403 `ip_not_allowed` from an address outside the range. `TestOpsAllowedIPs` (`gorbital/opshttp/allowed_ips_test.go`), which covers the proxy cases and the spoofing attempt, still passes unchanged.

#### OPS-2 — a separators-only `OPS_ALLOWED_IPS` failed open

`ipfilter.ParsePrefixes` skips empty items, so `","` or `" , "` parses to no ranges with no error; `len(allowed) == 0` then meant "install nothing" and `/ops/` answered every address, with no error and no log line. A genuinely malformed value such as `office` was, and is, refused at load.

**Fix.** `LoadConfig` refuses a value that lists no address range (`gorbital/config.go`). Leaving the variable unset is still how an app allows every address.

**Test.** `TestLoadConfigOpsAllowedIPs` (`gorbital/config_test.go`), cases `","` and `" , "`.

#### OPS-3 — the storage status echoes the driver's error (maintainer)

`GET /ops/storage` puts `err.Error()` from `storage.Ping` into the response body (`gorbital/opshttp/internal/usecase/storage.go:39-41`). S3 and Spaces SDK errors routinely carry the endpoint host name, bucket, region and request ID. It contradicts the policy stated three files away — `gorbital/opshttp/wiring.go:181-183`, "Errors are reported as fixed descriptions: driver messages can name hosts" — which the database checks do follow. Reachable with `ops.storage.read`, so by `ops_viewer`.

**Not fixed.** This is a faithful carry-over of v0.1 (`examples/v0.1/full-single/internal/modules/ops/usecase/storage.go:40` is the same line), and ADR-0083 freezes `/ops`'s responses as public API. Changing the field's content is the right thing but it is the maintainer's call against that freeze — it is also the kind of change that belongs in the v0.2 upgrade notes rather than a review commit. Recommended: a canned description in the response, the real error in the log, alongside a note in the upgrade notes.

### Development-only surfaces

Both development features hold up well, and their tests are the most hostile in the repository. The dev console and the `/ops` dev operator refuse tunnelled and forwarded requests, and the forwarding check runs **before** the token, so a tunnelled request with a valid token is still 403 (`modules/devconsole/devconsole.go:414-430`, `operator.go:36-49`). The tunnel token is read only from `CLOUDFLARE_TUNNEL_TOKEN` or `..._FILE`, passed to cloudflared only in its environment and never in argv, removed from the app's environment, redacted from every kept, printed or streamed line and from `cmd.Wait` errors, and never persisted — only the hostname is, at 0600 in a git-ignored directory. The test that proves it runs a fake cloudflared that deliberately prints the token and the decoded secret and fails on any occurrence in any status, log line, portal body or SSE stream.

The "Test now" sign-in tests create nothing: `TestSignInTestsCreateNothing` snapshots every `auth_*` table and `audit_events` before and after a full Google, GitHub, Apple and passkey and TOTP run and asserts equality, and asserts no `Set-Cookie`. The state is 32 bytes from `crypto/rand`, kept by SHA-256 in memory, single-use, and unknown states fall through to real sign-in. `CheckResultURL` refuses anything but loopback http(s), with no userinfo, fragment, whitespace or control characters, and is fuzzed on the built redirect, not just the input. The feature is gated at registration time on `APP_ENV == "development"` **and** `DEV_CONSOLE_TOKEN`, and `LoadConfig` refuses that token in production.

|---|---|---|---|
| DEV-1 | Low | `kill -9 orb dev` on macOS leaves cloudflared running, and the next `orb dev` republishes the new app through it | Maintainer |

#### DEV-1 — no orphan detection for cloudflared (maintainer)

`orb dev` puts cloudflared in its own process group and reaps it on every exit it handles (`defer d.tunnel.Close()` under `signal.NotifyContext`); Linux adds `Pdeathsig`, macOS and the BSDs have no equivalent (`cli/internal/tunnel/process_nolinux.go`). There is no pidfile and no orphan detection anywhere in `cli/`.

`kill -9` on `orb dev` — or any `os.Exit` or fatal runtime error that skips defers — leaves cloudflared forwarding `127.0.0.1:<app port>` to a public hostname indefinitely, with no `orb dev` for the developer to see. Worse, the **next** `orb dev` binds the same port, so the stale tunnel silently republishes the new app and a second tunnel starts alongside it.

**Not fixed.** The fix is a small feature, not a patch: record cloudflared's pid and start time in `.orb/portal/tunnel.json`, and on start verify and kill a recorded pid whose executable is cloudflared. That is new behaviour with its own failure modes (pid reuse, a developer's own cloudflared) and belongs in the tunnel's own change rather than a review commit. ADR-0086 already lists the gap; it should also say what the next start does about it.

### Tooling that writes into apps

Deny by default survives ejection: ejected code is byte-identical but for import paths and still calls `gorbital.Get`/`Post`, so `register` applies the sign-in check and the bearer requirement to anything not explicitly `guard.Public()`, and refuses a non-public route when the API declares no bearer scheme. `orb eject` copies no secrets — its source is the library module from the module cache, never the app. `orb gen module` emits a route table where every verb carries `guard.Permission` or `guard.OrgMember`. Neither `eject` nor `upgrade --layout` reads or writes `.env`: both use `git ls-files --cached --others --exclude-standard`, and `.env` is git-ignored. The v0.2 middleware order is v0.1's plus the `Timeout` step, and `carryMiddleware` inserts it in the same place for a custom stack.

|---|---|---|---|
| CLI-1 | Medium | `orb upgrade --layout v0.2` regraded org-scoped permissions to the platform `user` role past the twentieth resource | Fixed |
| CLI-2 | Info | `golang.org/x/text` in `cli` was two years behind and carried GO-2026-5970 | Fixed |
| CLI-3 | Info | `gorbital.lock` records the library's hash, not the ejected copy's, so an edited ejected module is invisible to `orb doctor` | Maintainer |

#### CLI-1 — org-scoped permissions regraded to `user`

`orb upgrade --layout v0.2` decides from `internal/app/permissions.go` whether a module's permissions belong to the organisation roles or to the platform `user` role, and wrote `OrgRoles: []string{"owner", "admin", "member"}` or `Roles: []string{"user"}` accordingly (`cli/internal/cli/upgrade_layout_wiring.go:435-443`). The decision read only the **first 20 lines** under the `//orb:anchor org-permissions` anchor:

```go
after, found := strings.CutPrefix(sectionAfter(string(src), recipes.OrgPermissionsAnchor), "")
return found && strings.Contains(firstLines(after, 20), name+"Permissions,")
```

`orb gen resource --scope org` inserts each new `<pkg>Permissions,` **right after the anchor**, so the oldest entries drift out of the window. In an app with more than twenty org-scoped resources, the oldest resources' read and write permissions were regraded to `user` — a role every signed-in account holds — instead of the organisation's roles. A module whose use case checks the permission on the actor then let any signed-in account read and write another organisation's resource. (Modules that authorise through `svc.orgs` are refused by the upgrade outright, which bounds this.) The `found` from `strings.CutPrefix(s, "")` is dead — that call is always `true` — which is cosmetic but hid how little the function checked.

**Fix.** Read the whole list, up to the line that closes the literal (`listEntries`), and drop the dead `found`.

**Test.** `TestOrgScopedReadsTheWholeList` (`cli/internal/cli/upgrade_layout_orgscoped_test.go`) builds a 40-entry list and checks the first, the twentieth, the twenty-first and the last, plus names outside the list, no anchor and no file. With the 20-line window restored it fails on `resource20` and `resource39`.

#### CLI-2 — `golang.org/x/text` in the CLI

`govulncheck` reports GO-2026-5970 (infinite loop on invalid input) against the CLI, reachable through pgxpool's connection-string normalisation from `internal/pgmeta`. Every other module already carried v0.41.0 or v0.42.0; `cli` was pinned to v0.29.0.

**Fix.** `golang.org/x/text` v0.42.0 (and `golang.org/x/sync` v0.23.0 with it). After the bump `govulncheck` reports nothing outside the standard library.

#### CLI-3 — the lock's ejected hash is the library's, not the copy's (maintainer)

`gorbital.lock` records, for each ejected module, the SHA-256 of the **library's** package at the time of ejection, and the ejected files are not added to `lock.Files` (`cli/internal/cli/eject.go:422-424`, `lock.go:323-337`). `orb doctor` compares the library's current hash with the recorded one (`doctor_main.go:281-293`). So an edit to `internal/modules/auth/**` in the app is invisible to `orb doctor` — which is the intended design, since an ejected module is the app's to edit — but so is tampering with the recorded hash: anyone who can commit can set it to the library's current hash and permanently silence the "port the fixes you need" warning, which is the only channel by which a library security fix reaches an ejected module. The lock has no self-checksum or signature.

**Not fixed.** It is a supply-chain design question, not a bug: any integrity marker inside the file is defeated by the same access that edits it, so the answer is either a detached signature or CODEOWNERS on `gorbital.lock` in the app's repository, both of which are the maintainer's to choose. Recommended: document in the CLI guide that `gorbital.lock` should be code-owner-protected in an app that ejects modules, and have `orb doctor` print the recorded hash so a reviewer can compare it with the tag.

## Reported and not confirmed

Three issues raised during the area reads did not survive verification, and are recorded so they are not raised again:

- **Custom guard errors leak internals.** `guard.Spec.Check`'s doc says an unmapped error becomes a 500 "logged once with the request ID", and `registry.refuse` passes the raw error to `huma.WriteErr` without logging. But `openapi.InstallErrors` routes any status ≥ 500 through `Mapper.Problem`, which logs the cause with the request ID and returns a generic detail. Verified directly: a guard returning `errors.New("plans: dial tcp 10.0.0.5:5432 … password=…")` answers `{"code":"internal_error","detail":"an internal error occurred"}`. Sound; only the test is missing (listed above).
- **`exceptCrossSitePosts` can be bypassed by path tricks.** The exemption is an exact match on `r.URL.Path` against two Apple paths, evaluated before routing. A path that does not match exactly is protected, and a path that matches routes to the same Apple endpoint, so it fails closed in both directions.
- **A failed `X-Forwarded-For` walk attributes the request to the proxy.** Real, but not reachable in the shipped deployment: it needs the attacker to control the **right-most** hop, which a normal appending proxy (`$proxy_add_x_forwarded_for`) prevents. Worth stating in the production guide for service-mesh deployments where the front proxy passes `X-Forwarded-For` through unchanged; not a finding against the library.

## Limitations

- **Internal reviewers**, as in v0.1. This is no substitute for the external review `v1.0.0` requires.
- **Scope:** the v0.2 diff. v0.1 code that did not move was not re-reviewed; the gorbital-web site, the Dev Portal frontend source and the client templates are outside this repository.
- **Third-party services** (Cloudflare, Resend, Google, Apple, GitHub, and the JWT providers) were reviewed only as the library calls them. DEV-1's residual risk in particular depends on Cloudflare's own header behaviour.
- **One platform.** The tunnel's process handling was reviewed on macOS and read for Linux; the Windows path (`Process.Kill()`, no process group) has no test.
