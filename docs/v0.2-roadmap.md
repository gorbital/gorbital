# v0.2 roadmap: a framework you import

**Status:** Proposed (2026-09-17), second draft after architecture review · **Target release:** `v0.2.0` · **Branch:** `v0.2` · **Builds on:** [ADR-0002](adr/0002-module-architecture.md), [ADR-0015](adr/0015-public-api-and-stability-tiers.md), [ADR-0017](adr/0017-application-lifecycle.md), [ADR-0019](adr/0019-module-dependency-rules.md), [ADR-0021](adr/0021-generator-operation-model.md), [ADR-0022](adr/0022-generated-application-layout.md)

`v0.1.0` gives an app its features by generating them into the app. `v0.2.0` moves the reusable part of that code into the library, so an app imports a working server and writes only its own modules:

```go
func main() {
	gorbital.Main(
		gorbital.WithAuth(authhttp.New()),               // sign-in: sessions, MFA, passkeys, social, API keys
		gorbital.WithModules(ops.Module(), modules.All()...), // /ops, then your modules
	)
}
```

```go
Routes: func(r *gorbital.Router, d gorbital.Deps) {
	h := &handler{db: d.DB, audit: d.Audit}
	books := r.Group("/v1/books")                    // every route requires sign-in unless marked public
	gorbital.Post(books, "", h.createBook,
		guard.Permission(PermWrite), guard.RateLimit(30, time.Minute), guard.Idempotent())
},
```

## Current state

Assessed on 2026-09-17 against `main` (`41f7c6b`), the golden apps and `portal-demo`.

| Finding | Evidence | Consequence |
|---|---|---|
| The library already has the building blocks | `httpx` (Recover, RequestID, TrustedProxies, AccessLog, SecureHeaders, CORS, CrossOrigin, BodyLimit, problem+json), `ratelimit` and `ratelimitpg`, `auth` (hashing, tokens, TOTP, API keys, `Middleware`, `Catalog`), `actor`, `idempotency`, `orgs`, `postgres`, `jobs`, `settings`, `flags`, `mail`, `storage`, `telemetry`, `observability` | v0.2 is mostly **composition and extraction**, not new behaviour |
| The wiring and the endpoints live in each app | `portal-demo/internal/app`: 10 027 lines (the middleware chain in `routes.go`, construction in `app.go`, `rate_limits.go`, `maintenance.go`, `permissions.go`); `internal/modules/{auth,ops,flags,mailevents}`: 16 963 lines; auth alone has 74 operations | Fixes reach apps only through `orb upgrade`'s three-way merge; every app carries ~27 000 lines it didn't write |
| Registering a module takes edits in four places | `internal/modules/<name>/module.go`, `internal/app/module_<name>.go` (error mappings), a line after `//orb:anchor modules` in `modules.go`, permissions in `permissions.go`; each operation is a verbose `huma.Register` with a hand-written `signedIn` wrapper | The boilerplate the user asked to remove |
| Protection is opt-in per operation | A route without the `signedIn` wrapper is public; the global per-IP limit covers `/v1/auth/` only | A forgotten wrapper is a security bug |
| Migrations are one ordered history | Library migrations are copied into `db/migrations` (`20260914000001_settings.sql` …), applied by goose from a separate command, never at startup ([ADR-0017](adr/0017-application-lifecycle.md)) | Moving modules into the library must keep the same version numbers so existing databases see no change |
| Jobs can be enqueued inside a transaction | `jobs.Client.InsertTx(ctx, tx, args, opts)` | Transactional side effects don't need a new event bus |
| Quality gates exist | CI: gofmt, vet, `go test -race`, golangci-lint, govulncheck, gitleaks, `apicheck`, `refdocs`, OpenAPI files match golden apps, new apps build and pass tests, scaffold compatibility | Reuse them; add what's missing: fuzz tests (none today), benchmark budgets (7 benchmark files, no budgets), v0.1-app-against-v0.2-library compatibility |

**The actual problem**, restated: apps own framework code they shouldn't have to own, adding a route takes too many edits, and protection depends on remembering a wrapper. The request for "Nest-style automatic routes" is one answer to the second part; the plan solves all three and treats route annotations as optional sugar on top of an explicit API.

## Goals and non-goals

**Goals**

1. A new Full app's own code is its modules, `main.go` and migrations; no framework wiring.
2. A route is one call (or one annotation) with its protection next to it; routes are **deny by default**.
3. Every sign-in feature of v0.1 comes from the library, with hooks for common changes and ejection for everything else.
4. **Existing v0.1 apps keep compiling against the v0.2 library without changes.** Converting to the new layout is opt-in (`orb upgrade`).
5. The HTTP contract of every built-in endpoint (paths, bodies, error codes, audit actions, permissions) is unchanged.
6. v0.1 documentation stays published unchanged; every v0.2 change is documented, including every public method and a real application using it.

**Non-goals for v0.2**

- A dependency injection container, reflection-based wiring or runtime registration by `init()`.
- File-based routing.
- A message bus, Redis or any second required datastore (PostgreSQL stays the only requirement, [architecture principle 5](architecture.md#2-principles)).
- New product features beyond the [committed security layers](#phase-11-security-layers).

## Architecture

### Layers

```text
your app (main.go, modules/, db/migrations)
   │ imports
   ▼
gorbital.dev/gorbital ─── gorbital.dev/gorbital/guard           ← NEW: composition library
   │ imports                                   (the only package that combines several modules)
   ▼
gorbital.dev/modules/*  (auth/authhttp, ops, flags/flagshttp, orgs/orgshttp, jobs, postgres, …)
   │ imports                                   (modules never import each other; unchanged)
   ▼
gorbital.dev  core      (httpx, ratelimit, actor, audit, mail, config, page, health, app)
   │ imports                                   (stdlib, OpenTelemetry API, golang.org/x; unchanged)
   ▼
standard library
```

The only rule that changes is at the top: `gorbital.dev/gorbital` may import several modules, as `internal/app` does today. It does not import optional drivers: storage backends, mail providers, `authhttp` and `orgshttp` are passed in by the app, so an app compiles only what it uses and the dependency graph of a small app stays small.

### Package responsibilities

| Package | Owns | Does not own |
|---|---|---|
| `gorbital.dev/gorbital` | Config loading, construction order, the default middleware stack, the router over Huma, `Module` and `Deps`, commands (`serve`, `migrate`, `openapi`, role commands), lifecycle via `app.Run` | Business rules, SQL, sign-in logic |
| `gorbital.dev/gorbital/guard` | Route-level allow/deny decisions and their OpenAPI description | Sessions, rate-limit storage |
| `modules/auth` (existing) | Building blocks: hashing, tokens, TOTP, API keys, `Middleware`, `Catalog` | HTTP endpoints |
| `modules/auth/authhttp` (new) | The 74 sign-in operations, their use cases, SQL and migrations; options and hooks | Routing or middleware of other modules |
| `modules/ops/opshttp`, `flags/flagshttp`, `mail/mailevents`, `orgs/orgshttp` (new) | Today's generated endpoints of the same names | — |
| The app | Its modules, migrations, configuration values, which built-in modules it mounts | Framework wiring |

### API tiers

| Tier | Where | Promise |
|---|---|---|
| Public | `gorbital.dev/gorbital`, `guard`, new `*http` packages, new `httpx` functions | Listed by `apicheck`; breaking changes only with an ADR, changelog and upgrade notes (v0) |
| Experimental | `gorbital.dev/x/...`, and route annotations until the [Phase 9 gate](#phase-9-route-annotations) | May change in any release |
| Internal | `internal/` | None |
| Generated | `modules.gen.go`, `routes.gen.go` | Regenerated freely; never edited; the generator's output format is versioned with `orb` |
| Owned scaffold | `main.go`, `modules/<name>/*`, ejected modules | The developer's code; `orb` never overwrites it without plan → diff → apply ([ADR-0021](adr/0021-generator-operation-model.md)) |

### Lifecycle

`gorbital.Main` is a thin, documented convenience over explicit steps an advanced app can call itself:

```text
gorbital.Main(opts...)
  ├─ parse subcommand            serve (default) · migrate · migrate-down · openapi · roles · grant-role · …
  ├─ gorbital.LoadConfig(config.OS) → (Config, error)          no global state; errors name the variable
  ├─ gorbital.New(ctx, cfg, opts...) → (*App, error)
  │     telemetry → postgres pool → audit → settings & flags registries (collected from modules)
  │     → stores → jobs → mail → auth → modules' Routes → middleware stack → handler
  ├─ (*App).Run(ctx)            app.Run: server + job workers + release heartbeat; signals; drain; shutdown order
  └─ exit code                  0 ok · 1 runtime error · 2 usage or configuration error
```

Migrations run only from `migrate` ([ADR-0017](adr/0017-application-lifecycle.md)). `(*App).Handler()` exists for tests and for mounting inside another server.

### Failure modes

| Failure | Behaviour |
|---|---|
| Invalid or missing configuration | `LoadConfig` returns every problem at once, naming the variable; exit code 2 |
| Two modules declare the same route, permission, setting, flag, job or error code | `New` fails before listening, naming both modules |
| A route has no auth decision | Impossible by construction: routes require sign-in unless `guard.Public()` |
| Database unreachable at start | `New` fails with the connection error (redacted URL); readiness stays false while it's down at runtime |
| Pending migrations | `New` starts and `/readyz` reports them (today's behaviour), `orb doctor` names them |
| A hook (`AfterLogin`) fails | Logged with the request ID; the sign-in succeeds |
| A hook (`BeforeLogin`, `OnRegister`) fails | The sign-in or registration is refused; `OnRegister` rolls back its transaction |
| A custom middleware stack omits recovery or authentication | Allowed (it is explicit code), with a startup warning and an `orb doctor` finding |
| Rate-limit store unavailable | Falls back to in-memory limits (today's `ratelimitpg` behaviour) and logs once |

## Decisions

Each becomes part of an ADR in Phase 0 and can be changed there; after Phase 0, a change needs a new ADR.

| # | Decision | Chosen | Rejected, and why |
|---|---|---|---|
| D1 | Import path | `gorbital.dev/gorbital`, its own Go module; call sites read `gorbital.Main`, `gorbital.Post` | `gorbital.dev/kit` (reads worse); growing core (its dependency budget forbids Huma and pgx) |
| D2 | Compatibility | **Additive.** No exported identifier of v0.1 changes meaning or is removed; v0.1 apps build against v0.2 (a CI job proves it). `orb upgrade` to the new layout is opt-in | A breaking v0.2 that forces every app to convert |
| D3 | Built-in features in `main.go` | **Explicit one-liners**: `gorbital.WithAuth(authhttp.New(...))`, `gorbital.WithModules(ops.Module(), …)`, `gorbital.WithStorage(s3.New(...))`. `orb new` writes them | Everything on implicitly (hides what an app contains, pulls every dependency into every app) |
| D4 | Construction | `LoadConfig` → `New` → `Run`, plus `Main` as convenience | Only `Run(cfg)` (hard to test and to embed) |
| D5 | Dependencies for modules | `gorbital.Deps`, a plain struct with documented, possibly-nil fields | A DI container; reflection; a service locator with `Get[T]` |
| D6 | Route declaration | Explicit `gorbital.Get/Post/…` inside `Module.Routes` is the primary API. Generic package-level functions, because typed Huma handlers can't be generic methods | Only annotations; file-based routing (one package per URL segment, nothing to "go to definition" on) |
| D7 | Nest-style annotations | `//gorbital:route` + `//gorbital:guard` generated into `routes.gen.go` calling D6's functions. Experimental until the [Phase 9 gate](#phase-9-route-annotations). Small grammar: no Go expressions in comments | Annotations carrying middleware expressions (code in comments, not type-checked) |
| D8 | Module discovery | `modules/modules.gen.go` written by `orb dev`/`go generate`, committed; the app builds without `orb` | `init()` self-registration (hidden) |
| D9 | Default protection | **Deny by default**: every route requires sign-in; `guard.Public()` opts out; `orb routes` lists public routes | Opt-in `guard.Auth()` (today's forgotten-wrapper bug) |
| D10 | Middleware | Every level takes `httpx.Middleware` (`func(http.Handler) http.Handler`). App: `WithMiddleware` (runs after authentication). Module: `Module.Middleware`. Group and route: `gorbital.Use`. Route-level middleware is adapted onto Huma with `humago.Unwrap`/`humago.NewContext` | A gorbital middleware type |
| D11 | Changing the built-in stack | `gorbital.WithStack(func(s gorbital.Stack) []httpx.Middleware)`: `Stack` has one field per built-in step; the function returns the order. Plain Go | Positional options `Before`/`After`/`Replace`/`Without` (a mini-language to learn) |
| D12 | Custom guards | `guard.New(guard.Spec{Name, Errors, Check})`; `Check` returns an error mapped like any other | Guards writing responses directly |
| D13 | Module layout | Flat by default (`module.go`, `handlers.go`, `store.go`); `orb gen module --layered` keeps `domain/usecase/repository/delivery` and its architecture test | Mandatory layers |
| D14 | Migrations | One ordered goose history. Library modules keep their existing version numbers and embed their files; `migrate` merges library files with `db/migrations` by version. App modules keep migrations in `db/migrations` (cross-module foreign keys stay possible) | Per-module version tables (breaks ordering across modules, changes existing databases) |
| D15 | Sign-in customisation | Options; hooks `BeforeLogin` (can refuse), `AfterLogin` (errors logged), `OnRegister` (in the registration transaction); `authhttp.RegisterFields[T]`; `Deps.Auth.SignIn` for new sign-in methods, which applies bans, MFA, audit, rate limits and transport | Copying auth into apps |
| D16 | Escape hatch | `orb eject <module>` copies a library module into the app as owned, layered code | None |
| D17 | Minimal preset | Keeps composing core packages directly (no database); `gorbital.New` requires PostgreSQL. Re-evaluated in Phase 3 against a measured dependency and binary-size budget | A database-optional facade (branches in every constructor) |
| D18 | Docs versions | `release/v0.1` frozen and published at `/v0.1/`; v0.2 written on `v0.2`, previewed at `/next/` | One set of docs edited in place |

## Engineering standards

Every phase passes these before it is marked done. Existing CI jobs are reused; new ones are added in Phase 0.

| Area | Gate |
|---|---|
| Formatting and analysis | `gofmt`, `go vet`, golangci-lint (staticcheck, errorlint, gosec as configured), `govulncheck` on every module |
| Tests | Table-driven unit tests; `go test -race` everywhere; database tests against Docker PostgreSQL (`pgtest`); HTTP tests through the real handler |
| Contracts | `apicheck` listings for every new exported identifier; OpenAPI of the golden apps unchanged except where the phase says so; **the v0.1.0 OpenAPI of `/v1/auth/*`, `/ops/*` and `/v1/flags` is a frozen fixture**; error codes, audit actions, permissions and settings keys compared with `docs/reference` |
| Compatibility | A CI job builds and tests an app generated by `orb v0.1.0` against the branch's library (D2); `TestScaffoldCompatibility` keeps running |
| Fuzzing | New `Fuzz*` tests for every parser the phase adds: route paths and parameters, annotation grammar, webhook signature headers, JWT headers, config values |
| Benchmarks with budgets | Recorded in `docs/benchmarks.md`, compared in CI with `benchstat` on the phases that touch them: route adapter overhead versus a direct `huma.Register` (target ≤ 1 extra allocation, ≤ 5 % latency); each guard on the allow path (0 allocations except rate limits); `gorbital.New` start time and memory versus v0.1 `full-single` (≤ +10 %); `go list -deps` count and binary size of the golden apps (no growth without a note) |
| Security | A threat model section in the phase's ADR for anything touching authentication, authorization, sessions, webhooks, tokens or uploads; findings fixed or recorded in `docs/security/` |
| Observability | Spans named by route pattern; guard refusals counted by guard name and route pattern (bounded cardinality); hooks traced; no per-request logs added at INFO |
| CLI | Every new command has `--json`, works with `--no-input`, documents its exit codes, and has golden tests for text and JSON output |
| Generated code | Compiles, passes `gofmt` and golangci-lint in a generated app, reads as hand-written Go, and is covered by golden files |
| Review | Each phase ends with a self-review against the [architecture review rules](#architecture) and a list of known gaps in this page's status table |

### Phase 1: Router, Module and Deps

**Goal:** a module declares everything about itself in one value, with explicit routes that are protected by default.

| # | Item |
|---|---|

## Not in v0.2

Considered during planning and deliberately left out. Each needs an ADR with a concrete use case before it is scheduled.

| Idea | Why not now | What to do instead today |
|---|---|---|
| Event bus or outbox module | Transactional side effects already work: `jobs.Client.InsertTx` enqueues in the same transaction as the write | Document the pattern in the *Receiving payment webhooks* recipe |
| Redis backends, cache module | PostgreSQL is the only required datastore; `ratelimitpg` and `idempotency` already share state across instances | An in-process cache in the app where measured |
| Response compression, ETag, load shedding | Usually done by the reverse proxy or CDN; adds buffering and edge cases to every response | Configure at the proxy; revisit with measurements |
| CAPTCHA module | Needs a provider choice and UI integration; the rate limits and bans already slow credential stuffing | `BeforeLogin` hook calling the provider |
| Outbound HTTP client with retries and circuit breaker | Useful, but a design of its own (retry budgets, idempotency of outbound calls) | `net/http` with timeouts and OpenTelemetry's `otelhttp` |
| Outgoing webhooks, upload handler | Product features with their own storage and delivery design | Jobs plus `modules/storage` signed URLs |
| WebSocket | No example needs it; SSE covers server-to-client streams | The existing streams in `observability` as a reference |
| File-based routing | See D6 | Explicit routes or annotations |

## Risks

| Risk | Mitigation |
|---|---|
| The public surface grows by hundreds of identifiers and 100+ operations to keep compatible | `apicheck`; frozen v0.1.0 contract fixtures; experimental tier for annotations; additive-only rule (D2) |
| Moving sign-in changes a security property by accident | Extraction without behaviour change first (Phase 5), contract tests, threat models, internal review before release |
| Hooks don't cover what real apps changed | Phase 10's upgrade report lists every customisation found; each becomes a hook or a documented reason to eject |
| `gorbital.New` becomes a god constructor | It only orders calls to existing constructors; every step stays callable on its own; documented construction order; D4 keeps it testable |
| Annotations become a second language | Gated (Phase 9), small grammar, no expressions in comments, explicit API always works |
| The facade pulls heavy dependencies into small apps | Drivers passed by the app (D3), dependency and binary budgets in CI, D17 for Minimal |
| Two doc versions double the writing | Methods generated; examples included from compiled code; v0.1 accepts only fixes |

## Changes from the first draft

The first draft (commit `38c0c33`) was reviewed on 2026-09-17 against the codebase and the project's principles. What changed and why:

| First draft | Now | Why |
|---|---|---|
| v0.2 as a breaking release that converts every app | **Additive**; v0.1 apps build against v0.2; conversion opt-in (D2) | Nothing forces a break: extraction adds packages; users upgrade when ready |
| Auth, ops and drivers on implicitly (`WithoutAuth` to remove) | **One explicit line per built-in** in `main.go` (D3) | What the app contains is visible; small apps don't compile what they don't use |
| `gorbital.Run(cfg)` only | `LoadConfig` → `New` → `Run`, plus `Main` (D4) | Testable, embeddable, errors reported instead of exiting |
| `guard.Auth()` added to each route | **Deny by default**, `guard.Public()` to opt out (D9) | A forgotten guard can't expose a route |
| `Before`/`After`/`Replace`/`Without`/`IKnowWhatImDoing` | `WithStack(func(Stack) []httpx.Middleware)` (D11) | Plain Go instead of a positional mini-language |
| Per-module migration tables | One goose history, same versions (D14) | Cross-module foreign keys, and existing databases see no change |
| Migrations as part of `Run` | Only from `migrate` | [ADR-0017](adr/0017-application-lifecycle.md): never implicitly at startup |
| Annotations as the default, with `use` expressions in comments | Explicit API first; annotations experimental and gated, no expressions (D6, D7) | Code in comments isn't type-checked; the explicit API solves most of the boilerplate |
| Auth moved and customised in one phase | Extraction unchanged (Phase 5), then options and hooks (Phase 6) | Regressions are visible when behaviour isn't changing at the same time |
| Test kit in the last phases | Phase 3 | Every later phase and example uses it |
| Redis, cache, compression, ETag, load shedding, CAPTCHA, HTTP client, outgoing webhooks, uploads, event bus, WebSocket | [Not in v0.2](#not-in-v02) | No committed use case; some contradict "PostgreSQL only"; `InsertTx` already covers transactional side effects |
| No quality gates beyond existing CI | [Engineering standards](#engineering-standards): fuzzing, benchmark budgets, v0.1-app compatibility job, frozen contracts, threat models | A framework's guarantees need tests that enforce them |
