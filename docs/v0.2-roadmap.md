# v0.2 roadmap: a framework you import

**Status:** Proposed (2026-09-17) · **Target release:** `v0.2.0` · **Branch:** `v0.2` · **Builds on:** [ADR-0002](adr/0002-module-architecture.md), [ADR-0019](adr/0019-module-dependency-rules.md), [ADR-0022](adr/0022-generated-application-layout.md), [ADR-0015](adr/0015-public-api-and-stability-tiers.md)

`v0.1.0` gives an app its features by generating them into the app: a new Full app holds about 27 000 lines that gorbital wrote (the whole middleware chain in `internal/app/`, the 74 sign-in routes in `internal/modules/auth`, the `/ops` API), and a fix to any of it reaches the app only through `orb upgrade`'s three-way merge. `v0.2.0` moves that code into the library. An app imports a working server, declares its own modules, and keeps only its own code:

```go
func main() {
	gorbital.Run(gorbital.FromEnv(),
		gorbital.WithModules(modules.All()...),
	)
}
```

```go
// createBook adds a book owned by the signed-in user.
//
//gorbital:route POST /v1/books
//gorbital:guard auth permission=books.book.write ratelimit=30/m idempotent
//gorbital:status 201
func (h *handler) createBook(ctx context.Context, in *createBookInput) (*bookOutput, error) {
```

Four rules hold for every phase:

| Rule | What it means |
|---|---|
| **The library owns behaviour and the default wiring** | Middleware order, sign-in, `/ops`, jobs, mail and settings come from `gorbital.Run`. The app writes its modules, configuration and migrations. This revises principle 3 of the [architecture](architecture.md) ("library for behaviour, generation for wiring") by an ADR in Phase 0 |
| **Still traceable, still no reflection** | Generated code is committed Go (`routes.gen.go`, `modules.gen.go`) that calls `gorbital.Post(...)`: "go to definition" works, the compiler checks every route, and the app builds and deploys without `orb` ([architecture principles](architecture.md#2-principles) 1 and 8) |
| **Secure by default, and hard to turn off by accident** | Every route gets the full stack; removing recovery or authentication needs an explicit option; custom sign-in methods create sessions only through the library, so bans, MFA, audit and rate limits still apply |
| **Nothing ships undocumented** | A phase is done only when its decision record, guide pages, method reference, example and upgrade notes are written and the docs build. See [Documentation rules](#documentation-rules) |

## Decisions

Taken during planning on 2026-09-17. Each becomes (or is recorded in) an ADR in Phase 0 and can still be changed there; after Phase 0 closes, a change needs a new ADR.

| # | Decision | Chosen | Rejected, and why |
|---|---|---|---|
| D1 | The package users import | `gorbital.dev/gorbital`, its own Go module, package `gorbital` (call sites read `gorbital.Run`, `gorbital.Post`) | `gorbital.dev/kit` (`kit.Run` says less); growing the core `gorbital.dev` module (its dependency budget forbids Huma and pgx) |
| D2 | Where guards live | `gorbital.dev/gorbital/guard` (`guard.Auth()`, `guard.Permission(...)`) | Guards inside `httpx` (they need Huma operations and OpenAPI) |
| D3 | Layering | One new layer above the modules: `app → gorbital.dev/gorbital → modules/* → core`. Only `gorbital.dev/gorbital` may import several modules; modules still never import each other | Letting modules import each other |
| D4 | How routes are declared | `//gorbital:route` annotations above handler methods, generated into `routes.gen.go` (the Nest.js model: the route is declared on the function); writing `gorbital.Post(...)` by hand always works too, and both mix in one module | File-based routing like Next.js: one Go package per URL segment, awkward `[id]` folders, nothing to "go to definition" on |
| D5 | Default URL prefix | The module folder names the default group prefix (`modules/books` → `/v1/books`) unless a `//gorbital:group` says otherwise | No default (more annotation noise) |
| D6 | How modules are found | `orb dev` and `go generate` write `modules/modules.gen.go`; it is committed | Registration at runtime by `init()` (hidden registration) |
| D7 | Module layout | Flat by default (`module.go`, `handlers.go`, `store.go`, `migrations/`); `orb gen module --layered` keeps today's `domain/usecase/repository/delivery` and its architecture test | Mandatory layers (most of the per-module code) |
| D8 | Middleware type | Every level (app, module, group, route) takes the existing `httpx.Middleware`, `func(http.Handler) http.Handler`; route-level middleware is adapted onto Huma operations with `humago.Unwrap` and `humago.NewContext` | A gorbital-specific middleware type |
| D9 | The default stack | Named steps (`MWRecover` … `MWIdempotency`) that apps can place around, replace or remove; removing `MWRecover` or `MWAuth` needs `gorbital.IKnowWhatImDoing()` | An unnamed fixed chain |
| D10 | Sign-in customisation | Options (`auth.Password()`, `auth.Google()`, …), hooks (`BeforeLogin` refuses, `AfterLogin` errors are logged and never block, `OnRegister` runs in the registration transaction), `auth.RegisterFields[T]`, and `d.Auth.SignIn` for new sign-in methods | Copying the auth module into every app |
| D11 | Full control | `orb eject <module>` copies a library module into the app as owned code | No escape hatch |
| D12 | Existing apps | `orb upgrade` converts a v0.1 app: generated files it finds unchanged are deleted in favour of the library; changed ones stay as ejected modules, with a report of which changes could become hooks | Supporting only new apps |
| D13 | Version | `v0.2.0`, a breaking v0 release with upgrade notes ([ADR-0015](adr/0015-public-api-and-stability-tiers.md)); the HTTP contract of the built-in endpoints does not change | Waiting for `v1.0.0` (the external security review is unrelated) |
| D14 | Docs versions | `v0.1` docs are frozen on branch `release/v0.1` and stay published; `v0.2` docs are written on `v0.2` and published as a preview until the release | Editing the one set of docs in place (loses what v0.1 users read) |

## Documentation rules

Documentation is part of every phase, not a phase of its own.

### Versions and branches

| Branch (gorbital and gorbital-web) | Holds | Changes allowed |
|---|---|---|
| `release/v0.1` | The code and docs of `v0.1.0` as published (gorbital `main` at `41f7c6b`) | Security fixes and factual corrections only, cherry-picked, each listed in the v0.1 changelog |
| `v0.2` | The `v0.2.0` work; phase branches merge into it | Everything in this roadmap |
| `v0.2/phase-N` | One phase, stacked on the previous | That phase's items |
| `main` | The latest release | Moves to `v0.2` when `v0.2.0` is released (Phase 12) |

The docs site (gorbital-web `apps/docs`) serves every version side by side (Phase 0, items 3–8):

| URL | Content | Source |
|---|---|---|
| `docs.gorbital.dev/…` | The latest release: `v0.1` until `v0.2.0` ships, then `v0.2` | `main` |
| `docs.gorbital.dev/v0.1/…` | Always `v0.1`; links to it never break | `release/v0.1` |
| `docs.gorbital.dev/next/…` | The unreleased `v0.2`, with a "not released yet" banner | `v0.2` |

A version switcher sits in the header of every page and keeps the reader on the same page in the other version when it exists. Older versions carry a banner linking to the latest.

### What every phase writes

| Deliverable | Where | Checked by |
|---|---|---|
| Decision record (new or updated ADR) | `docs/adr/00NN-*.md`, listed in `docs/adr/README.md` | Link check |
| Guide pages for what users do | `docs/guides/` (and `docs/sign-in/`, `docs/start/` when relevant) | Docs build |
| **Methods** entries for every exported identifier the phase adds or changes: signature, what it does, parameters, return values and errors, a runnable example, "since v0.2.0", related methods | Generated into `docs/methods/` from Go doc comments and `Example` functions by `internal/tools/refdocs`, with curated text in its overlay | `refdocs -check` fails on an exported identifier without a doc comment and an example |
| **Examples**: the phase's features used in a real application | `docs/examples/` pages, code in `examples/apps/` | The example apps build and their tests pass in CI; pages include code from those files by marker, so the docs can't drift from the code |
| Changelog | `CHANGELOG.md`, section `Unreleased (v0.2.0)` | Review |
| Upgrade notes | `docs/guides/upgrade-notes.md`, section `Upgrading to v0.2.0` | Review |
| API listings | `api/*.txt` (`apicheck`) | CI |
| Navigation | `docs/docs.json` | Docs build |
| Roadmap status | This page's table | Review |
| Synced site | gorbital-web `pnpm sync-docs`, committed on the matching branch | Docs build, preview deploy of `/next/` |

### New docs tabs

- **Methods.** The library's Go API, one page per package, grouped as the [target API](#target-api) table: every function, type, option and error with its signature, description, example and the version it arrived in. Searchable, and linked from guides wherever a method is named. Replaces reading `api/*.txt` or pkg.go.dev for day-to-day use.
- **Examples.** Real applications built with gorbital, explained step by step:
  - **Shelfie**, the running example: a reading-tracker API for a mobile and web app. Books (`createBook`), shelves, custom middleware (`requireClientVersion`), guards and per-route rate limits, sign-in with hooks and extra registration fields, phone-code sign-in as a custom method, cover uploads, reminder emails as jobs, book clubs as organisations, webhooks to a partner, tests with the test kit, deployment.
  - **Recipes**, each a small runnable app: a multi-tenant invoicing SaaS (organisations, row-level security, tenant resolver); a payments webhook receiver (HMAC verification, idempotency, outbox); a public API with API keys and usage limits; an internal admin tool (IP allow list, recent re-authentication); a mobile backend with external JWTs (Auth0 or Clerk) instead of built-in sign-in; live notifications with SSE.

Each phase adds the Shelfie chapter and the recipes its features make possible; Phase 12 reviews them end to end.

## Risks

| Risk | Mitigation |
|---|---|
| The library's stable surface grows by hundreds of identifiers and 100+ HTTP operations | `apicheck`, OpenAPI contract tests against `v0.1.0`, the experimental `x/` tier for anything unproven |
| Hooks don't cover what real apps changed in their generated auth | Phase 8's upgrade report lists every customisation found; each one either becomes a hook before release or is documented as a reason to eject |
| Upgrading customised apps is hard to get right | Ejection as the safe fallback; end-to-end upgrade tests on three kinds of v0.1 app; `UPGRADE-v0.2.md` written into each app |
| Annotations become a second language to learn | Hand-written `gorbital.Post` always works; the checker gives file:line errors with suggestions; the grammar fits on one docs page |
| Docs for two versions drift or double the work | Methods pages are generated; examples are included from compiled code; `v0.1` accepts only fixes |
| Moving auth changes a security property by accident | Contract tests, unchanged audit actions and error codes, and the Phase 6 review (item 73) |
