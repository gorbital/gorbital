# Your main.go

In a v0.2 app, `cmd/api/main.go` is the whole composition root: one call to `gorbital.Main` that names what the app contains. gorbital loads the configuration, builds the database pool, stores, job workers, email delivery and middleware in a fixed order, serves the API, and shuts it all down cleanly. Your code is your modules and your migrations. The package is `gorbital.dev/gorbital` ([Methods](../methods/gorbital.md)); the decisions are [ADR-0081](../adr/0081-a-framework-you-import.md) and [ADR-0083](../adr/0083-modules-stack-migrations-and-ejection.md).

> **Status: v0.2, in progress.** `gorbital.Main` is in the library. Sign-in (`authhttp`) and `/ops` arrive as modules in Phases 4 and 5 of the [v0.2 roadmap](../v0.2-roadmap.md); until then an app on `Main` has no sign-in of its own, and every route that isn't `guard.Public()` answers 401. Apps generated by `orb` v0.1 keep their `internal/app` and work unchanged.

## The file

<!-- include examples/apps/shelfie/cmd/api/main.go#main -->

| Option | What it adds |
|---|---|
| `WithName("shelfie")` | The service name in logs, traces and metrics, the OpenAPI title and the database connections' application name. Without it, the last element of the module path |
| `WithModules(modules.All()...)` | The app's modules. `modules.All` is generated from `internal/modules` ([below](#the-module-list)) |
| `WithMigrations(migrations.FS)` | The app's own migrations, the embedded `db/migrations` |
| `WithAuth(a)` | The authenticator: its middleware sets who is calling; `authhttp.New()` from Phase 5, or your own |
| `WithStorage(s)`, `WithStorageFunc(open)` | File storage other than the local driver, such as S3 ([configuration](environment-variables.md#apps-on-gorbitalmain)) |
| `WithMailer(s)`, `WithMailerFunc(open)` | The email provider for `MAIL_DELIVERY=provider`, which production requires |
| `WithMiddleware(mw...)`, `WithMiddlewareFunc(build)` | Your middleware, after the built-in stack ([the middleware stack](middleware-stack.md)) |
| `WithStack(build)` | A different order for the built-in stack |
| `WithLogger(logger)` | Your own `*slog.Logger` instead of the one built from `APP_LOG_LEVEL` and `APP_LOG_FORMAT` |

Every option is a line you can read: nothing is on because of a default you can't see, and an app compiles only the drivers it names.

## Commands

The first argument chooses what the program does:

| Command | What it does | Needs |
|---|---|---|
| `serve` (or nothing) | Loads the configuration, builds the app and serves it until SIGINT or SIGTERM | `APP_ENV`, `DATABASE_URL` |
| `migrate` | Applies pending migrations: the library's, the modules' and yours in one history, then River's job tables | `APP_ENV`, `DATABASE_URL` |
| `migrate --status [--json]` | Reports pending migrations and changes nothing; `orb doctor` reads the JSON | Same |
| `migrate-down` | Rolls back your most recent migration. Development only | Same |
| `openapi [--dir api]` | Prints the OpenAPI document, or writes `openapi.json`, `postman_collection.json` and `llms.txt` into the directory. Reads no environment and needs no database: modules register their routes with zero `Deps` | Nothing |
| `version [--json]` | Prints the build's version, commit and Go version | Nothing |
| `help` | Lists the commands, including those modules add | Nothing |

```bash
go run ./cmd/api migrate
go run ./cmd/api                       # serve
go run ./cmd/api openapi --dir api
```

The server never migrates on its own ([ADR-0017](../adr/0017-application-lifecycle.md)): run `migrate` before starting a new version, as a release step. When migrations are pending, the server logs a warning at start.

Built-in modules add commands of their own; from Phase 5, sign-in adds `grant-role`, `revoke-role` and the others of v0.1's `cmd/api`.

### Exit codes

| Code | When |
|---|---|
| 0 | Success, and a clean shutdown |
| 1 | A runtime error: the database is unreachable, a migration failed, the server stopped unexpectedly |
| 2 | A usage or configuration error: an unknown command or flag, an invalid environment variable, a production-only refusal such as `migrate-down` with `APP_ENV=production`, or a missing provider (`MAIL_DELIVERY=provider` without `WithMailer`) |

Every configuration problem is reported at once, one line per variable:

```text
shelfie: invalid configuration:
APP_ENV must be development or production, got "staging"
APP_CORS_ORIGINS: "http://app.example.com" must use https in production
```

## What serve builds, in order

1. **Logging and telemetry**: the logger, traces and metrics (OTLP when `OTEL_EXPORTER_OTLP_ENDPOINT` is set), the metrics listener on `METRICS_ADDR`, the dev console's log buffer and the hourly log archive.
2. **PostgreSQL**: the pool, its readiness check, and warnings for pending migrations and row-level security problems.
3. **The audit log** (`audit_events`).
4. **Declarations**: the built-in runtime settings (`mail.*`, `maintenance.*`, retention and incidents), then every module's permissions, settings and flags. A duplicate stops the start naming both modules.
5. **Stores**: runtime settings and feature flags, loaded before anything serves.
6. **Email delivery**: SMTP to `orb dev`'s mail catcher or Mailpit in development, your provider in production, skipping suppressed addresses.
7. **Shared rate limits, idempotency keys, file storage, request metrics.**
8. **Jobs**: the built-in cleanup, incident and retention jobs, then every module's `Jobs`, then the job client and its definitions manager.
9. **The mailer modules use** (`Deps.Mailer`): it queues each email as a job, with the sender from the `mail.*` settings.
10. **Release tracking and the request collector**, and in development with `DEV_CONSOLE_TOKEN` the [dev console](dev-console.md).
11. **The API**: `/version`, every module's routes, `/docs` when enabled, `/livez` and `/readyz`.
12. **The middleware stack** around it ([the middleware stack](middleware-stack.md)).

Every step is a public constructor of a library module, so you can read what it does, or do it yourself.

## Shutting down

On SIGINT or SIGTERM, `serve`:

1. makes `/readyz` answer 503, so load balancers stop sending traffic;
2. waits the drain delay: 5 seconds in production, none in development;
3. stops taking requests and lets the server and the workers (settings and flags listeners, the job client and definitions manager, the release heartbeat, the request collector, the metrics listener) finish, for up to 25 seconds;
4. closes resources in the reverse order they were opened: the dev console, the database pool, the log archive, telemetry last.

A second signal during shutdown stops at once.

## The module list

`internal/modules/modules.gen.go` lists every directory under `internal/modules` whose package declares `func Module() gorbital.Module`:

<!-- include examples/apps/shelfie/internal/modules/modules.gen.go -->

Never edit it. It is regenerated by:

- `orb dev`, before each build, when a module was added or removed;
- `go generate ./internal/modules`, which runs `orb gen modules` (the file carries the directive);
- `orb gen modules` directly (`--dry-run` shows the change, `--json` for scripts).

The file is committed, so the app builds without `orb`.

## Without Main

`Main` is a convenience over three calls you can make yourself, for example to serve the app inside another server or to run it from your own command-line tool:

```go
ctx := context.Background()
cfg, err := gorbital.LoadConfig(config.OS)
if err != nil {
	log.Fatal(err)
}
opts := []gorbital.Option{gorbital.WithModules(modules.All()...), gorbital.WithMigrations(migrations.FS)}
app, err := gorbital.New(ctx, cfg, opts...)
if err != nil {
	log.Fatal(err)
}
log.Fatal(app.Run(ctx))
```

`app.Handler()` is the whole API behind the middleware stack, `app.Deps()` the dependencies modules receive, and `app.Close(ctx)` releases everything when `Run` isn't called. `gorbital.Migrate(ctx, cfg, os.Stdout, opts...)` applies migrations.
