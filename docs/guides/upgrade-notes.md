# Upgrade notes

What changes for existing apps in each release, and what to do that `orb upgrade` can't do for you. How upgrades work: [ADR-0016](../adr/0016-scaffold-compatibility-and-upgrades.md) and [ADR-0050](../adr/0050-upgrades-and-adding-features.md); commands: [CLI reference](cli.md).

`v0.1.0` is the first public release: apps created with it or later start here, and each later release adds its section above this line. Apps created with a development build of `orb` before `v0.1.0` follow [Before v0.1.0](#before-v010-development-builds).

## Upgrading to v0.2.2

**Your app needs no code changes.** The library is additive: every name v0.2 apps use keeps working, `apicheck` records one changed line and no removed one, and the HTTP contract, problem codes, permission names, role names and migration versions of an existing app are unchanged. `go get gorbital.dev@v0.2.2` and its modules, and you are done.

Two things changed in the CLI, and one of them may be in your scripts.

### `orb eject` is gone

```text
$ orb eject auth
orb eject was removed in v0.2.2.
```

Since v0.2.1 `orb new` writes sign-in and organisations into the app, so there was nothing left for the command to do ([ADR-0092](../adr/0092-what-the-framework-owns.md)). The name still answers for this release and explains itself; it will be gone entirely in the next.

**If you scripted it**, remove the call: the modules it copied are already in `internal/modules`. **If you were about to run it** to take `opshttp`, `flagshttp` or `mailevents` into your app, you can't any more — they stay in the library, because they are plumbing rather than business rules. Tell us if that blocks you.

`orb new --no-eject` is gone with it. There is one shape of Full app.

### The example applications moved

They are at [github.com/gorbital/examples](https://github.com/gorbital/examples) now. If you cloned this repository to read Plateful or a recipe, that is where to look ([ADR-0093](../adr/0093-the-examples-repository.md)).

### What you may want to do, but need not

None of this is required. Everything below keeps working under its old name for all of v0.x.

| If you have | You may prefer | Why |
|---|---|---|
| `guard.OrgMember(p)` | `guard.Scope(p)` | The same guard under your app's own tenancy |
| `Permission.OrgRoles` | `Permission.ScopeRoles` | Same values; one name for every kind of tenant |
| `Platform.SetOrgAuthorizer` | `Platform.SetScope` | Lets you name your tenancy and validate your own IDs |
| `postgres.WithOrg` | `postgres.WithScope` | The same function; one session setting either way |

None of these carries a `Deprecated` marker on purpose: `staticcheck` turns those into build failures, and your app should not go red because we renamed something in a patch.

**To call your tenant something other than an organisation**, see [Tenancy](tenancy.md). In short: `orgshttp.ScopeName("merchant", "merchants", "merchantId")` changes the routes, the path parameter, the refusal code and the OpenAPI tag, and nothing in your database. Changing a public URL is a breaking change for your own clients, so add the new path and keep the old one until your next API version.

**`actor.Actor.OrgID` and the `gorbital.org_id` session setting keep their names**, whatever you call your tenant. Both now mean *the scope*. Renaming them would change what every audit row you have already written, and every row-level-security policy in your live database, means.

### New things you may want

- **Turn sign-in methods off.** `authhttp.New(authhttp.Methods(authhttp.MethodPassword, authhttp.MethodOperators))` serves 29 operations instead of 74, declares no settings, jobs or permissions for the rest, and answers their paths with 404. The migrations stay, so the tables are there, empty, and turning a method back on later is this one line and no migration.
- **State a resource's access rule.** `orb gen module --scope user|tenant|public|custom`. `custom` writes a policy file you own; until you implement it the module answers 501 rather than serving every row.
- **`orb routes`** now shows which scope each route requires.

## Upgrading to v0.2.0

v0.2.0 moves routes, guards, the middleware stack, the application itself, sign-in, the operations API and organisations from generated code into the library ([ADR-0081](../adr/0081-a-framework-you-import.md), [v0.2 roadmap](../v0.2-roadmap.md)). **It is additive.** An app created with `v0.1.0` builds and passes its tests against `v0.2.0` with no code changes, and CI checks that on every change:

```bash
go get gorbital.dev@latest
go get gorbital.dev/modules/...@latest    # every gorbital.dev module your go.mod requires
go mod tidy && go build ./... && go test ./...
go install gorbital.dev/cli/cmd/orb@latest
orb doctor
```

Nothing else is required. Staying on the v0.1 layout is a choice, not a delay: `orb upgrade` keeps merging the v0.1 templates into your app, `orb gen resource`, `orb gen job` and `orb dev` behave as before, and no v0.2 feature is withheld from you — `timeout`, `ipfilter`, `webhook` and `modules/jwt` all work in a v0.1 app. Moving to the new layout is the opt-in `orb upgrade --layout v0.2` ([below](#moving-a-v01-app-to-the-v02-layout)).

### What a v0.1 app notices

Everything a `v0.1.0` app sees change, whether or not it moves layout.

| Change | What to do |
|---|---|
| `orb` is `v0.2.0`. `orb upgrade`'s report and `--json` gain a `layout` field; `orb doctor --json` gains `layout` too; `orb add orgs --json` gains it | Nothing. Your app's `gorbital.lock` records no layout, so `orb upgrade`, `orb add orgs` and `orb add mail` rebuild and merge it from the v0.1-layout templates this `orb` still carries, never the new ones. Scripts that parse `orb doctor --json` or `orb upgrade --json` should ignore unknown fields, as they already should |
| The new error codes `request_timeout`, `ip_not_allowed`, `invalid_token`, `reauthentication_required`, `invalid_webhook_signature`, `request_too_large` and `registration_closed` exist in the library | Nothing, and this is deliberate: `timeout`, `ipfilter`, `webhook` and `jwt` are packages of their own (not part of `httpx`) precisely so that a v0.1 app, which records the problem codes of every `gorbital.dev` package it links in `api/surface.json`, does not fail its `TestPublicSurface` ([stability](stability.md#adding-error-codes), [ADR-0085](../adr/0085-security-layers.md#package-moves-2026-09-17)). The codes appear only once you link the package |
| Request timeouts: `gorbital.dev/httpx/timeout` ([Security layers](security-layers.md)) | Nothing. A v0.1 app has no `APP_REQUEST_TIMEOUT` and no deadline, as before. To add one, put `timeout.New(30*time.Second)` in `internal/app/routes.go` near the top of the chain, then record the new code with `go test ./internal/app -run TestPublicSurface -update`. Check your slowest legitimate endpoint (long report exports, large uploads) against the value you pick: a handler that has not started writing when the deadline passes gets 503 `request_timeout` |
| IP filtering: `gorbital.dev/httpx/ipfilter` ([Security layers](security-layers.md)) | Nothing. To restrict `/ops` to an office or VPN range, wrap it with `ipfilter.New(allow, deny)` in `internal/app/routes.go` **after** `httpx.TrustedProxies`, so the client address is the real one, and record the new code as above. In an app on `gorbital.Main` this is the `OPS_ALLOWED_IPS` variable instead |
| Signed webhooks: `gorbital.dev/webhook`, and `resend.VerifyWebhook` now built on it | Nothing: `resend.VerifyWebhook`'s API, errors and behaviour are unchanged. New receivers can use `webhook.NewHMAC` (GitHub, Shopify, Slack) or `webhook.NewStandard` (Standard Webhooks, Svix, Resend, Clerk) |
| External identity providers: `gorbital.dev/modules/jwt` ([Security layers](security-layers.md)) | Nothing. It is an alternative authenticator for apps on `gorbital.Main`, not a change to sign-in |
| Code written against the **v0.2 branch** used `httpx.Timeout`, `httpx.IPFilter`, `httpx.ParsePrefixes` and `httpx.ErrDenyAll` | Those names never shipped. Use `timeout.New`, `ipfilter.New`, `ipfilter.ParsePrefixes` and `ipfilter.ErrDenyAll` |
| **The dev console (`/_dev/*`) and the development operator on `/ops/` refuse requests carrying forwarding headers** (`Forwarded`, `X-Forwarded-For`, `X-Forwarded-Host`, `X-Real-IP`, `True-Client-IP`, `CF-Connecting-IP`, `CF-Ray`, `CDN-Loop`), so a tunnel or proxy on the developer's machine, which connects from loopback, can't reach them ([ADR-0086](../adr/0086-dev-portal-tunnel.md)) | This is the one change that can break a working local setup. If you reach `/_dev/` — or `/ops/` with the console token — through a local reverse proxy of your own (nginx, Caddy, Traefik, a tunnel) that adds any of those headers, you now get 403 `forbidden`, or no development operator on `/ops/`. Call the app directly, or go through `orb dev`'s portal proxy. Production is unaffected: the dev console is development-only. A variable named `CLOUDFLARE_TUNNEL_TOKEN` or `CLOUDFLARE_TUNNEL_TOKEN_FILE` in `.env` no longer reaches the app under `orb dev` |
| Dev Portal: `orb dev --tunnel quick\|named` and the Tunnel screen ([Tunnel](../dev-portal/tunnel.md)); the Routes screen shows guards, public routes, middleware and sources; the generators hub has Module and Middleware forms | Nothing in the app. Install `cloudflared` yourself to use tunnels — `orb` never downloads it. Tunnels are development-only |
| Everything a v0.1 app does not have: `gorbital.Main`, `gorbital.New`, `gorbital.Module`, `guard`, `gorbitaltest`, `httpx.Maintenance`, `httpx.Capture`, `authhttp`, `opshttp`, `flagshttp`, `mailevents`, `orgshttp`, `orb gen module`, `orb gen middleware`, `orb gen modules`, `orb routes`, `orb eject` | Nothing. Your app keeps `internal/app`, `internal/modules/{auth,ops,flags,mailevents,orgs}`, `internal/jobs`, `cmd/api`, `cmd/migrate` and `cmd/seed`, which serve the same contract as the library modules that replaced them. To see the new layout without touching your app, follow [Shelfie](../examples/shelfie/00-start-a-project.md) or run `orb new --preset full` in a scratch directory |

### If you move to the v0.2 layout

These only apply once you run `orb upgrade --layout v0.2` (or start a new app with `orb new`). The move itself is [below](#moving-a-v01-app-to-the-v02-layout).

| Change | What to do |
|---|---|
| `main.go` is `gorbital.Main` with one option per built-in: `gorbital.WithAuth(authhttp.New())`, `gorbital.WithModules(opshttp.Module(), flagshttp.Module(), mailevents.Module())`, `orgshttp.Module(auth)` in a multi-tenant app, `gorbital.WithMigrations(migrations.FS)` ([Your main.go](main-go.md)) | Read `main.go` after the move: it is the whole composition, and nothing is implicit. `gorbital.WithStack` replaces the middleware list in `internal/app/routes.go`; `orb doctor` warns if a custom stack leaves out `Recover` or `Auth` |
| `APP_REQUEST_TIMEOUT` (default 30s) is on, as the `Timeout` step of the default stack; `gorbital.Timeout(d)` shortens it per route | **Check your slowest endpoint.** A handler that has not started writing when the deadline passes answers 503 `request_timeout`. Raise `APP_REQUEST_TIMEOUT`, or give the route its own `gorbital.Timeout`. Streaming routes and `http.ResponseController` keep working |
| `OPS_ALLOWED_IPS` limits `/ops/` to client addresses after `APP_TRUSTED_PROXIES`, answering 403 `ip_not_allowed` **before** the sign-in check | Optional, and off when unset. Set it only once `APP_TRUSTED_PROXIES` is right for your deployment, or you will filter on your load balancer's address and lock yourself out of `/ops` |
| Environment variables are v0.1's, with the same names, defaults and production refusals, read by `gorbital.LoadConfig`, which reports every problem at once ([environment variables](environment-variables.md#apps-on-gorbitalmain)) | Nothing: your `.env` and your deployment's variables carry over. Configuration errors now exit with status 2 and list every problem instead of the first |
| The commands move from `cmd/migrate`, `cmd/seed` and `cmd/api` onto one binary: `./cmd/api serve`, `migrate [--status [--json]]`, `migrate-down`, `openapi [--dir]`, `version`, `help`, and sign-in's `roles`, `grant-role`, `revoke-role`, `reset-mfa`, `rotate-auth-keys`, `auth-providers` and `seed [--email]` | **Update your deployment scripts, Dockerfile and CI**: `go run ./cmd/migrate` becomes `./api migrate`, `cmd/seed` becomes `./api seed`. Wrong arguments now exit with status **2**, not 1; scripts that test for a non-zero status are fine, scripts that test for `1` are not. Output is otherwise v0.1's |
| Migrations: `gorbital.Migrate` merges the library's history (under the versions your `db/migrations` copies already hold, from a frozen table), the built-in modules' migrations and your own `db/migrations`, then River's | Nothing, and this is the point: a database your v0.1 app migrated has **nothing to apply**. Identical copies collapse; a copy whose content you edited fails the merge naming both files, which is a real conflict to resolve, not a warning. `db/migrations` is untouched by the move, so your modules' tests keep migrating from it |
| Routes answer 401 before the request body is validated; v0.1 validated first and the use case answered 401. Sign-in's own routes keep v0.1's order | Nothing, unless a client relies on getting 422 for an invalid body **without** a token. Your use cases' permission checks are unchanged until you turn them into `guard.Permission`, which changes 403s the same way |
| Every route requires an authenticated actor unless it carries `guard.Public()` | Check the routes you meant to be public after the move: `orb routes --public` lists them. A route you forget to mark answers 401 rather than leaking. Read `orb routes` as a lower bound on protection, not the whole story: it lists the guards on a route, and a module that checks a permission inside its use case — as the built-in `/ops` modules do, keeping v0.1's behaviour — shows only `authenticated` there while still answering 403 without the permission |
| `api/surface.json` records only the app's **own** names; error codes and audit actions that moved into the library are no longer yours | Run `go test ./internal/modules -run TestPublicSurface -update` and read the diff: what disappears should be exactly the built-in modules' names. After `orb eject`, the ejected module's names become yours again and `orb eject` records them for you |
| `api/openapi.json` gains `x-gorbital-guards` on guarded operations, and `/ops`'s example values come from the library (`acme-api-7d9f8-x2kq` as the example instance host instead of your app's name) | Nothing: both are documentation. `git diff api/openapi.json` after the move should show only these. Anything else is worth reading closely |
| Generated clients: the anonymous body schema of `POST /v1/orgs` may get another name (`CreateInputBody` instead of `CreateInputBody1`) when no module registered that name first; its content is unchanged. An anonymous request with an invalid body to an organisation operation gets 401 instead of 422 | Regenerate your client and diff it. Rename the type in code that referred to it |
| Challenge tokens of second-factor sign-ins that started with Google, Apple, GitHub or a module's own method end in `.` and the method, such as `.google`, so they are longer. A password sign-in's token is v0.1's | Treat them as opaque strings, as the API always documented. Clients that store, validate or truncate them need checking |
| `orb gen job` refuses; `orb add orgs` needs a new database; `orb add rls` works; `orb gen resource` runs `orb gen module` | Declare jobs in a module's `Jobs` field instead of `orb gen job`. `orb add orgs` in an app on `gorbital.Main` can't apply the organisations module's v0.1 migration versions to a database already migrated past them, so convert before you have data, or move the data yourself |
| `gorbital.lock` records `"layout": "v0.2"`, and `ejected` once you eject a module | Scripts reading the lock see the new fields. An `orb` built before v0.2.0 refuses a lock with `ejected` |
| `orb eject <auth\|flags\|mailevents\|ops\|orgs>` copies a built-in module into `internal/modules/<module>` as code you own, at the version you build with ([Ejecting a module](ejecting-a-module.md)) | Use it when an option or a [hook](sign-in-hooks.md) can't do what your app needs. The API, database and behaviour don't change. `orb doctor` warns when the library's copy changes afterwards, quoting the changelog, and going back is manual. Eject `orgs` before `auth` |
| What v0.1 apps changed in their auth module is now options and hooks: `MinPasswordLength`, `PasswordPolicy`, `RequireMFA`, `APIKeyMaxTTL`, `WithoutRegistration`, `Brand`, `RouteMiddleware`, `BeforeLogin`, `AfterLogin`, `OnRegister`, `RegisterFields[T]`, `(*Authenticator).SignIn` ([Configuring sign-in](configuring-sign-in.md)) | `authhttp.New()` without options is v0.1's sign-in exactly. Reach for an option, then a hook, then a sign-in method of your own, and only then `orb eject auth`. `orb upgrade --layout v0.2` lists every change it found in your auth module and which of these could replace it |
| An app on `gorbital.Main` with `opshttp` but **no** `authhttp` has no role holding `ops.auth.read` or `ops.auth.write` | Only relevant with an authenticator of your own (such as `modules/jwt`): grant those permissions to its actors, or `/ops/auth/*` answers 403 for everyone |

### Moving a v0.1 app to the v0.2 layout

`orb upgrade --layout v0.2` is the opt-in move ([Upgrading apps](../start/upgrading.md#move-to-the-v02-layout), walkthrough: [Upgrading a v0.1 app](../examples/recipes/upgrading-a-v0.1-app.md)). Staying is a choice, not a delay: a v0.1 app keeps its layout, `orb upgrade` keeps merging its templates, and nothing in v0.2 requires the move.

| Change | What to do |
|---|---|
| `orb upgrade --layout v0.2` converts a Full app of the v0.1 layout: generated code it finds unchanged is deleted (the library runs it), a changed built-in module is kept as the app's own code the way `orb eject` writes one, the app's own modules are converted where they are, and `internal/app`, `internal/jobs`, `cmd/migrate` and `cmd/seed` go. `gorbital.lock` records `"layout": "v0.2"` and any kept module under `ejected`; the app gets `UPGRADE-v0.2.md` | Run `orb upgrade` and commit it first: the move needs the app on this release's v0.1 templates. Then `orb upgrade --layout v0.2 --dry-run`, read the plan, and run it without `--dry-run`. Afterwards: `go test ./...`, `orb doctor`, then commit. Read the diff of `api/` before you do: `api/openapi.json` gains `x-gorbital-guards` on every route and its `/ops` instance example takes the app's name, and `api/surface.json` and `api/openapi.baseline.json` are rewritten, because the built-in modules' error codes, roles and jobs are the library's from then on and the file records only the app's own names. A large deletion there is the move working, not a loss. Nothing is committed for you, so `git restore . && git clean -fd` undoes the move |
| An example module you never changed (`ping`, and `projects` when its wiring can't be converted mechanically, such as in a multi-tenant app) is written from the v0.2 templates, which `orb gen module` produces: its request schemas are named after their operations and refuse unknown properties, where the v0.1 generated module accepted them | Nothing if your clients send only the documented fields. Otherwise restore the module from git after the move (`git checkout <before> -- internal/modules/<name>`) and convert it by hand, or add the fields to the schema |
| The copies of the library's migrations stay in `db/migrations` | Nothing: `gorbital.Migrate` reads a copy with the same version and identical content as the same migration, so a database migrated by the v0.1 app has nothing to apply. Delete the copies when nothing else reads them; module tests that migrate with `db/migrations` do |
| Changes orb can't carry over stop the move and are listed (a changed generated file of the composition root, a module whose wiring uses values `internal/app` built, jobs in `internal/jobs`, settings or flags declared in `internal/app`, an organisation-scoped module of a multi-tenant app that authorises through the organisations module's catalog) | Make them by hand where they belong — `main.go`'s options, a module's `Settings`, `Flags` or `Jobs`, a [hook](sign-in-hooks.md) — and run the move again; or run it with `--allow-manual`, which converts the rest and keeps those files in `_upgrade-v0.1/` for you to finish. `internal/app`'s own HTTP tests are not ported to `gorbitaltest` for you |
| Flags: `--dry-run`, `--diff`, `--json`, `--allow-dirty`, `--allow-manual`, `--yes`, `--no-input`, `--skip-tidy`, `--skip-build` | Use `--dry-run` then `--diff` before the real run. The move refuses a dirty tree unless you pass `--allow-dirty`, and git is the undo button |

## Before v0.1.0 (development builds)

Before `v0.1.0`, apps could be created with development builds of `orb` from a gorbital checkout (`--local`). The sections below take such an app to `v0.1.0`: read every section, newest first, down to the one for the build that created your app. `orb upgrade` rebuilds what gorbital wrote from the release or commit in `gorbital.lock`; when the lock records neither, name the commit of the gorbital checkout that created the app: `orb upgrade --from <commit>`. The pre-release tags of those builds were never public and no longer exist. Numbers such as v0.5 or v1.1 in older decision records name internal development milestones, not releases.

### Upgrading to v0.1.0

Includes the fixes from the internal security review ([report](../security/2026-09-internal-review.md), [ADR-0053](../adr/0053-internal-security-review.md)) and the operations and integrations work: per-organisation settings ([ADR-0056](../adr/0056-per-organisation-settings.md)), feature flags ([ADR-0057](../adr/0057-feature-flags.md)), API keys and service accounts ([ADR-0058](../adr/0058-api-keys-and-service-accounts.md)), GitHub sign-in ([ADR-0059](../adr/0059-github-sign-in.md)), idempotency keys ([ADR-0060](../adr/0060-idempotency-keys.md)), the row-level security option ([ADR-0061](../adr/0061-row-level-security.md)), the email suppression list with Resend webhooks ([ADR-0062](../adr/0062-resend-webhooks-and-suppression-list.md)), Prometheus metrics ([ADR-0063](../adr/0063-prometheus-metrics.md)), live observability with incidents ([ADR-0064](../adr/0064-live-observability-and-incidents.md)) and the local dev console APIs ([ADR-0065](../adr/0065-local-dev-console-apis.md)), and the Dev Portal ([ADR-0066](../adr/0066-dev-portal.md)). Rows are ordered by what you must do: first the changes to make **before deploying**, then changes your frontend or scripts may need, then what happens on its own.

#### Before deploying

| Change | What to do |
|---|---|
| **`APP_ENV` is required** ([ADR-0020](../adr/0020-constructors-and-configuration.md)). Apps refuse to start without it instead of assuming development (HTTP-6) | Check every deployment sets `APP_ENV=production` (the generated Dockerfile does; custom images, systemd units and platform configs may not) and that `.env` has `APP_ENV=development`. `orb dev` sets development for you; plain `go run ./cmd/api` in a Minimal app needs `APP_ENV=development`. If your own tests call `LoadConfig`, set `APP_ENV` in them. `orb upgrade` brings `config.go` and `main.go`; `go run ./cmd/api openapi` needs no environment |
| **API docs are off in production by default** ([ADR-0027](../adr/0027-api-contract-and-docs.md)). `APP_DOCS_ENABLED` defaults to `false` when `APP_ENV=production`, and turning docs off now also stops serving `/openapi.json` and `/openapi.yaml` (HTTP-3) | To keep a public API reference in production, set `APP_DOCS_ENABLED=true`. `orb upgrade` brings the `routes.go` change (`openapi.WithoutSpecEndpoints()` when docs are off). Google and Apple web sign-ins without `return_to` land on `/docs`: pass `return_to` from your frontend |
| **`APP_CORS_ORIGINS` must use https in production** (HTTP-4) | Replace any `http://` origin in production with its https address; otherwise the app refuses to start and names it. Origins with user info, a path, query or fragment are refused in every environment (`httpx.CORS`) |
| **`APP_TRUSTED_PROXIES`** | Behind a load balancer or reverse proxy, **set it before deploying** to their CIDR ranges (such as `10.0.0.0/8`). Otherwise every client shares the balancer's per-IP budget, and logs and audit events show the balancer's address |
| **Clients can't choose their request ID or trace** ([ADR-0007](../adr/0007-observability.md), [ADR-0030](../adr/0030-context-and-correlation.md)). The app generates `X-Request-ID` and starts a new trace for each request, linked to an incoming `traceparent`; incoming baggage is ignored; spans' `client.address` is the resolved client, not `X-Forwarded-For`. New `APP_TRUSTED_CALLERS` lists callers whose request IDs and trace context are kept (HTTP-1, HTTP-5) | If a gateway or internal service assigns request IDs or traces you rely on, set `APP_TRUSTED_CALLERS` to its ranges (client addresses after `APP_TRUSTED_PROXIES`; list your load balancer only if it sets those headers itself and drops clients' values). `orb upgrade` brings `config.go`, `app.go` and `routes.go`. Library users: `httpx.RequestID()` no longer accepts incoming IDs; use `httpx.RequestIDFrom(ranges)` and pass `telemetry.WithTraceContextFrom(ranges)` to `Setup` |
| **Unverified accounts are deleted after 7 days** by `auth_cleanup` (`auth.unverified_account_ttl`), freeing their addresses; accounts with a Google or Apple sign-in are kept ([ADR-0038](../adr/0038-authentication-v0-2.md)) | If you create unverified accounts on purpose (for example, invitations to set a password later), raise the setting **before deploying**: `PUT /ops/settings/auth.unverified_account_ttl` up to `2160h` with a reason. The first run after upgrading deletes existing unverified accounts older than the TTL, up to 10 000 per run |
| **More changes need a reason** ([ADR-0033](../adr/0033-background-jobs.md), [ADR-0037](../adr/0037-email-setup-and-delivery.md)). Settings `mail.from_name`, `mail.from_email`, `mail.reply_to`, `auth.verification_code_ttl`, and in multi-tenant apps `orgs.invitation_url` and `orgs.invitation_ttl` (OPS-9); changing a job's timeout, `max_attempts` or queue, and pausing a queue (OPS-2) | Scripts calling `PUT /ops/settings/…` for these keys, `PUT /ops/jobs/definitions/…` with those fields, or `POST /ops/queues/{name}/pause` must send `"reason"` (otherwise 422 `setting_reason_required` or `job_reason_required`). `orb upgrade` brings the ops module changes |
| **`jobs.Manager.PauseQueue` always returns `ErrReasonRequired`** (deprecated) | Code of your own calling `PauseQueue` must switch to `PauseQueueWithReason(ctx, name, reason)`; interfaces listing `PauseQueue`/`ResumeQueue` should list `PauseQueueWithReason`/`ResumeQueueWithReason`. The Full apps' ops module does this after `orb upgrade` |
| **Sign-ins without `return_to` end at `AUTH_DEFAULT_RETURN_TO`** ([ADR-0059](../adr/0059-github-sign-in.md)).
