# Upgrade notes

What changes for existing apps in each release, and what to do that `orb upgrade` can't do for you. How upgrades work: [ADR-0016](../adr/0016-scaffold-compatibility-and-upgrades.md) and [ADR-0050](../adr/0050-upgrades-and-adding-features.md); commands: [CLI reference](cli.md).

`v0.1.0` is the first public release: apps created with it or later start here, and each later release adds its section above this line. Apps created with a development build of `orb` before `v0.1.0` follow [Before v0.1.0](#before-v010-development-builds).

## Upgrading to v0.2.0 (unreleased)

v0.2.0 is being built on the [v0.2 roadmap](../v0.2-roadmap.md). It is additive ([ADR-0081](../adr/0081-a-framework-you-import.md)): an app created with v0.1.0 builds and passes its tests against v0.2.0 with `go get` and no code changes, and CI checks that on every change. Moving an app to the new layout (built-in sign-in and `/ops` from the library, `gorbital.Main` in `main.go`) will be an opt-in `orb upgrade`; this section lists what to do as each phase lands.

| Change | What to do |
|---|---|
| `gorbital.Main`, `gorbital.New`, `gorbitaltest` and `httpx.Maintenance` are added (Phase 3) | Nothing: a v0.1 app keeps its `internal/app`, `cmd/api` and `cmd/migrate`. To try the new layout, start from [Shelfie](../examples/shelfie/00-start-a-project.md); moving an existing app waits for `orb upgrade --layout v0.2` (Phase 9) |
| `orb dev` rewrites `internal/modules/modules.gen.go` before builds when the file exists | Nothing in a v0.1 app, which has no such file |
| The operations API, client flags and email events as built-in modules: `opshttp`, `flagshttp`, `mailevents` (Phase 4); `OPS_ALLOWED_IPS`; `Module.RateLimiters`, `Module.Retention`, `Module.Platform`; `gorbital.Customize` | Nothing: a v0.1 app keeps its generated `internal/modules/{ops,flags,mailevents}`, which serve the same contract. An app on `gorbital.Main` adds `gorbital.WithModules(opshttp.Module(), flagshttp.Module(), mailevents.Module())` ([Ops API](ops-api.md#adding-it-to-an-app)); with `authhttp` as the authenticator, `/ops` lists sign-in's methods, rate limiters and accounts retention as v0.1 did. Without `authhttp`, `ops.auth.read` and `ops.auth.write` (sign-in methods and rate limits) are held by no role: an authenticator of your own grants them to its actors. `opshttp.SignInMethods` and `opshttp.SignInMethod`, which existed only on the v0.2 branch, are gone: an authenticator reports its methods with a `SignInMethods(gorbital.Config) []gorbital.SignInMethod` method |
| Sign-in in the library: `gorbital.dev/gorbital/authhttp` (Phase 5), v0.1's auth module moved unchanged ([authentication](authentication.md#in-an-app-on-gorbitalmain)) | Nothing in a v0.1 app, which keeps `internal/modules/auth`, `internal/app` and `cmd/api`. An app on `gorbital.Main` adds `gorbital.WithAuth(authhttp.New())`; its environment variables are v0.1's, and a database migrated by a v0.1 app migrates as a no-op. Scripts calling the sign-in commands through `Main` get exit status 2, not 1, for wrong arguments |
| Security layers: `gorbital.dev/httpx/timeout`, `gorbital.dev/httpx/ipfilter`, `gorbital.dev/webhook`, `guard.Webhook`, `gorbital.dev/modules/jwt` ([Security layers](security-layers.md)) | Nothing: they are opt-in, and their new error codes (`request_timeout`, `ip_not_allowed`, `invalid_token`) are in packages a v0.1 app doesn't link, so its `api/surface.json` and `TestPublicSurface` are unchanged. A v0.1 app can add `timeout.New`, and an `ipfilter.New` in front of `/ops`, in `internal/app/routes.go`; then record the new codes with `go test ./internal/app -run TestPublicSurface -update`. `resend.VerifyWebhook` behaves as before. Code written against the v0.2 branch's `httpx.Timeout`, `httpx.IPFilter`, `httpx.ParsePrefixes` and `httpx.ErrDenyAll` uses `timeout.New`, `ipfilter.New`, `ipfilter.ParsePrefixes` and `ipfilter.ErrDenyAll` |
| `orb gen module`, `orb gen middleware`, `orb routes` and new `orb doctor` checks (Phase 8, [Generating code](generating-code.md)) | Nothing. In a v0.1 app `orb gen resource` is unchanged and `orb gen module` points at it; `orb routes` works there without guards; `orb doctor --json` gains the field `layout`. In an app on `gorbital.Main`, `orb gen resource` now runs `orb gen module` |
| Security layers: `httpx.Timeout`, `httpx.IPFilter`, `gorbital.dev/webhook`, `guard.Webhook`, `gorbital.dev/modules/jwt` ([Security layers](security-layers.md)) | Nothing: they are opt-in. A v0.1 app can add `httpx.Timeout`, and an `IPFilter` in front of `/ops`, in `internal/app/routes.go`; `resend.VerifyWebhook` behaves as before |

## Before v0.1.0 (development builds)

Before `v0.1.0`, apps could be created with development builds of `orb` from a gorbital checkout (`--local`). The sections below take such an app to `v0.1.0`: read every section, newest first, down to the one for the build that created your app. `orb upgrade` rebuilds what gorbital wrote from the release or commit in `gorbital.lock`; when the lock records neither, name the commit of the gorbital checkout that created the app: `orb upgrade --from <commit>`. The pre-release tags of those builds were never public and no longer exist. Numbers such as v0.5 or v1.1 in older decision records name internal development milestones, not releases.

### Upgrading to v0.1.0

Includes the fixes from the internal security review ([report](../security/2026-09-internal-review.md), [ADR-0053](../adr/0053-internal-security-review.md)) and the operations and integrations work: per-organisation settings ([ADR-0056](../adr/0056-per-organisation-settings.md)), feature flags ([ADR-0057](../adr/0057-feature-flags.md)), API keys and service accounts ([ADR-0058](../adr/0058-api-keys-and-service-accounts.md)), GitHub sign-in ([ADR-0059](../adr/0059-github-sign-in.md)), idempotency keys ([ADR-0060](../adr/0060-idempotency-keys.md)), the row-level security option ([ADR-0061](../adr/0061-row-level-security.md)), the email suppression list with Resend webhooks ([ADR-0062](../adr/0062-resend-webhooks-and-suppression-list.md)), Prometheus metrics ([ADR-0063](../adr/0063-prometheus-metrics.md)), live observability with incidents ([ADR-0064](../adr/0064-live-observability-and-incidents.md)) and the local dev console APIs ([ADR-0065](../adr/0065-local-dev-console-apis.md)), and the Dev Portal ([ADR-0066](../adr/0066-dev-portal.md)). Rows are ordered by what you must do: first the changes to make **before deploying**, then changes your frontend or scripts may need, then what happens on its own.

The first run after upgrading deletes existing unverified accounts older than the TTL, up to 10 000 per run |

| **`jobs.Manager.PauseQueue` always returns `ErrReasonRequired`** (deprecated) | Code of your own calling `PauseQueue` must switch to `PauseQueueWithReason(ctx, name, reason)`; interfaces listing `PauseQueue`/`ResumeQueue` should list `PauseQueueWithReason`/`ResumeQueueWithReason`. The Full apps' ops module does this after `orb upgrade` |
| **Sign-ins without `return_to` end at `AUTH_DEFAULT_RETURN_TO`** ([ADR-0059](../adr/0059-github-sign-in.md)). A Google, Apple or GitHub browser sign-in that names no `return_to`, or fails before its `return_to` is known, redirected to `APP_PUBLIC_URL/docs`, which is 404 in production since docs are off there. Production apps with Google, Apple web (`APPLE_SERVICES_ID`) or GitHub sign-in **refuse to start** without `AUTH_DEFAULT_RETURN_TO`, naming it; in development it still defaults to the API docs (and is required when `APP_DOCS_ENABLED=false`). It must be an absolute URL on `APP_PUBLIC_URL` or an `APP_CORS_ORIGINS` origin, https in production, without `#` | **Set `AUTH_DEFAULT_RETURN_TO` on every production instance before deploying**, to a page of your frontend that reads `#error=…` and `#mfa_challenge_token=…` (such as `https://app.example.com/signed-in`). `orb upgrade` brings `social.go`, `config.go`, `app.go` and `.env.example`. Passing `return_to` on every sign-in is still recommended |
| **Hourly log archive** ([ADR-0079](../adr/0079-hourly-log-archive.md), [guide](observability.md#the-hourly-log-archive)). Full apps gain the runtime setting `logs.archive.enabled` (off by default), `LOG_ARCHIVE_DIR` in `config.go` and `.env.example`, `internal/app/logarchive.go`, and a second `telemetry.WithLogTee` in `app.go` | `orb upgrade` brings the files; then re-record `api/surface.json` (the new setting key). | **Branded emails** ([ADR-0078](../adr/0078-branded-email-layout.md)). Full apps gain `(*App).brand()` in `internal/app/mail.go`; `app.go` passes it to `authlib.NewBrandedEmails` (and `orgslib.NewBrandedEmails`), `mail_previews.go` renders the previews and the test message with it | `orb upgrade`. | **Turning on row-level security (optional, multi-tenant apps)** ([ADR-0061](../adr/0061-row-level-security.md), [guide](row-level-security.md)). #### Frontends, scripts and data to check

| Change | What to do |
|---|---|
| **Google and Apple sign-in link an existing account only for addresses the provider manages** (Gmail, the account's Google Workspace domain, iCloud, Apple relay). Others get 403 `social_link_required` (web: `#error=social_link_required`); the signed-in owner links with the new `POST /v1/auth/identities` ([ADR-0046](../adr/0046-google-and-apple-sign-in.md), AUTH-M-1) | `orb upgrade` brings the endpoint and use cases. Frontends: on `social_link_required`, ask the person to sign in with their password, then link with an ID token (Google Identity Services, Sign in with Apple JS or the native SDKs) and a nonce from `POST /v1/auth/{provider}/nonce`. Existing links are kept; to review links made by the old rule, compare `auth_identities.email` domains with the rule above |
| **Accounts that Google or Apple sign-in creates for an address the provider doesn't manage are unverified** (`email_verified` false) until verified by email; proving the address by email while not signed in to that account ends its sessions and removes the provider link | Nothing for Gmail, Workspace, iCloud or Apple relay addresses. Frontends: offer "verify your email" to such users while they are signed in. Accounts created before stay verified; to review them, list `auth_identities` whose email domain isn't one the provider manages |
| **Registering again before verifying keeps the password only if it's the same.** A different password removes it; verifying an address (code, password reset, Google or Apple link) ends sessions and removes passkeys, authenticator app, recovery codes and identities added before (AUTH-S-1) | Frontends: after verifying, if sign-in answers `invalid_credentials`, offer "forgot password". Accounts verified earlier with a password set by an earlier registrant can't be told apart; if you suspect pre-registration abuse, look for `auth.user.registered` followed by verification from a different IP and ask those users to reset their password |
| **`grant-role` refuses accounts whose email address isn't verified** | Have the user verify (or reset the password) first. Roles already granted to unverified accounts stay; find them with `SELECT u.id FROM auth_users u JOIN auth_user_roles r ON r.user_id = u.id WHERE u.email_verified_at IS NULL AND u.deleted_at IS NULL` and revoke them |
| **Email addresses with uppercase non-ASCII letters or case-folding look-alikes (such as the Kelvin sign) are refused** as `invalid_email` (`auth.NormalizeEmail`, AUTH-S-3) | Existing accounts keep working when their owners type the address in lowercase. To find accounts registered with such addresses: `SELECT id FROM auth_users WHERE deleted_at IS NULL AND email <> lower(email) AND email ~ '[^[:ascii:]]'`; review them, since a look-alike may hold someone else's normalized address |
| **New recovery codes have 16 characters** (`xxxx-xxxx-xxxx-xxxx`, 80 bits) (AUTH-M-4) | Existing codes keep working. Frontends that check code length: accept up to 19 characters. If your database or a backup may have leaked, ask users with two-factor authentication to replace their codes (`POST /v1/auth/mfa/recovery-codes`) |
| **Multi-tenant apps: organisations and invitations need a verified address and have per-user limits.** A user owns at most `orgs.max_owned` (20) organisations and sends at most `orgs.user_invitations_per_hour` (50) invitations across organisations; new error code `too_many_orgs` (409) ([ADR-0048](../adr/0048-organisations-v0-4.md), ORG-3) | Raise the settings through `/ops/settings` (reason required) if your product needs more.
