# Security layers

Four layers you add when your app needs them: a **request timeout**, an **IP filter**, **signed webhook** verification and **external identity provider** tokens (JWT). Each is plain Go you can use with any `net/http` handler; in a gorbital app they sit in the middleware stack or next to a route. Decision and threat model: [ADR-0085](../adr/0085-security-layers.md).

| Layer | Protects against | API |
|---|---|---|
| [Request timeout](#request-timeout) | Slow queries and stuck dependencies holding connections and database slots | `timeout.New(d)` in `gorbital.dev/httpx/timeout` ([Methods](../methods/httpx-timeout.md)) |
| [IP filter](#ip-filter) | Operational endpoints reachable from any network | `ipfilter.New(allow, deny)`, `ipfilter.ParsePrefixes` in `gorbital.dev/httpx/ipfilter` ([Methods](../methods/httpx-ipfilter.md)) |
| [Signed webhooks](#signed-webhooks) | Forged, replayed or oversized provider webhooks | `guard.Webhook(v)` ([Methods](../methods/gorbital-guard.md#Webhook)), `gorbital.dev/webhook` ([Methods](../methods/webhook.md)) |
| [External identity providers](#external-identity-providers-jwt) | Accepting forged, expired or misdirected tokens from Auth0, Clerk, Supabase, Firebase or Cognito | `gorbital.dev/modules/jwt` ([Methods](../methods/modules-jwt.md)) |

Each layer with an error code of its own is a package of its own, so apps that don't use it don't carry the code in their recorded surface ([stability](stability.md#adding-error-codes)).

> **Status in v0.2 previews.** The layers are in the library. Apps on `gorbital.Main` get the request timeout in their default stack, and `/ops` behind `OPS_ALLOWED_IPS` with the built-in operations module. The recipes *Mobile backend with an external identity provider* and *Receiving payment webhooks* come with later phases of the [roadmap](../v0.2-roadmap.md#phase-10-security-layers); until then, add the other layers to your chain yourself as shown below.

## Request timeout

**Apps on `gorbital.Main`** have it already: the `Timeout` step of the [middleware stack](middleware-stack.md), set by `APP_REQUEST_TIMEOUT` (default `30s`, `0` turns it off). A route or group that must answer sooner gets `gorbital.Timeout(d)`:

```go
exports := r.Group("/v1/exports", gorbital.Timeout(5*time.Second))
```

`gorbital.Timeout` can only **shorten** the app's timeout (a context deadline can't be extended). For a route that needs longer, raise `APP_REQUEST_TIMEOUT`, or leave `s.Timeout` out with `gorbital.WithStack` and give the other groups their own `gorbital.Timeout`; better still, move the slow work into a [background job](background-jobs.md).

**Any other `net/http` app**, such as one generated by `orb` v0.1, adds the middleware to its chain:

```go
import "gorbital.dev/httpx/timeout"

handler := httpx.Chain(mux,
	httpx.Recover(logger),
	httpx.RequestID(),
	httpx.AccessLog(logger),
	timeout.New(30*time.Second),
	// …
)
```

A v0.1 app then records the new code: `go test ./internal/app -run TestPublicSurface -update`.

Each request's context gets a deadline. Pass `r.Context()` (or the Huma handler's `ctx`) to every query and outgoing call, and they stop at the deadline.

| When the deadline passes | What happens |
|---|---|
| The handler hasn't written anything | The client gets `503 request_timeout` straight away, with the request ID. Anything the handler writes afterwards is discarded: `Write` reports success, so frameworks that treat a failed write as a bug (Huma panics) stay quiet, while `Flush`, `Hijack` and deadline changes return `http.ErrHandlerTimeout` |
| The handler has started its response (status, body, flush) | Nothing is replaced: the deadline only cancels the context, and the response ends when the handler returns |

- **Streaming works**: nothing is buffered, `Flush`, trailers and `http.ResponseController` behave as without the middleware. But a stream's context is cancelled at the deadline, so long-lived streams (server-sent events) belong on routes without a timeout.
- **Install it after `Recover` and `RequestID`**, so panics are recovered and the 503 carries the request ID.
- **Choose `d` below your load balancer's idle timeout** and above your slowest legitimate request. 30 seconds suits most JSON APIs; reports and exports usually belong in [background jobs](background-jobs.md).
- Cost: about 1 µs and 12 allocations per request.

**What it doesn't do.** It can't stop a handler that ignores its context: the handler keeps its goroutine, and its connection stays open until it returns (an HTTP/1.1 client already has the complete 503). It doesn't limit how long a client takes to send its request; `httpx.Server` sets the connection read and write timeouts for that.

## IP filter

**Apps on `gorbital.Main` with the operations API** (`opshttp.Module()`) set `OPS_ALLOWED_IPS` to a comma-separated list of ranges and addresses ([environment variables](environment-variables.md#operations)):

```bash
OPS_ALLOWED_IPS=10.8.0.0/16,2001:db8:42::/48,203.0.113.7
```

`LoadConfig` parses it with `ipfilter.ParsePrefixes` and reports a bad entry with the other configuration errors, and every `/ops/` route runs `ipfilter.New` with it as the allow list, first among the route's middleware: before the sign-in check, guards and input parsing ([ops API](ops-api.md#restricting-ops-to-your-network)). Unset, nothing changes.

**Any other `net/http` app**, or other routes, use the middleware directly:

```go
import "gorbital.dev/httpx/ipfilter"

allow, err := ipfilter.ParsePrefixes(os.Getenv("OPS_ALLOWED_IPS")) // "10.0.0.0/8, 2001:db8::/32, 203.0.113.7"
if err != nil {
	return err
}
opsOnly, err := ipfilter.New(allow, nil)
if err != nil {
	return err
}
mux.Handle("/ops/", opsOnly(opsHandler))
```

| Rule | Behaviour |
|---|---|
| Address | `RemoteAddr` after `httpx.TrustedProxies`: behind a load balancer, set `APP_TRUSTED_PROXIES`, or every client has the balancer's address |
| Deny and allow | A request in a deny range is refused; with an allow list, a request in no allow range is refused. Deny wins |
| Empty lists | Empty allow allows everything not denied; both empty changes nothing |
| Refusal | `403 ip_not_allowed`; the response doesn't echo the address |
| IPv6 | IPv4-mapped addresses (`::ffff:10.0.0.1`) compare as IPv4; zones (`%en0`) are ignored |
| Refused at start | Invalid ranges; a deny range covering every address (`0.0.0.0/0`, `::/0`: list the allowed ranges instead); an allow range inside a deny range, which could never match |

A request whose `RemoteAddr` isn't an address (a Unix socket) is refused.

**What it doesn't do.** It isn't authentication: `/ops` still needs its sessions, roles and two-factor authentication, and an attacker inside an allowed network gets no further than before. Whole-app network rules belong in your firewall or load balancer.

## Signed webhooks

Providers sign each webhook with a secret you share with them. `guard.Webhook` checks the signature **before the body is parsed**, so an unsigned request never costs a JSON decode or learns what validation would say.

```go
payments, err := webhook.NewStandard(webhook.StandardConfig{
	Secrets: []string{cfg.PaymentsWebhookSecret.Reveal()}, // "whsec_…"
})
if err != nil {
	return err
}

gorbital.Post(r, "/v1/webhooks/payments", h.paymentEvent,
	guard.Public(),                                   // senders have no session
	guard.Webhook(payments, guard.WebhookBodyLimit(256<<10)))
```

| Request | Response |
|---|---|
| Signed with a configured secret, timestamp within 5 minutes | Reaches the handler with the exact body that was verified |
| Missing or malformed headers, wrong signature, body changed, older or newer than 5 minutes | `401 invalid_webhook_signature` (the same for every reason) |
| Body larger than the limit (default 1 MiB) | `413 request_too_large`, before verifying |
| A verifier that fails for another reason | `500`, logged |

### Senders

| Sender | Verifier |
|---|---|
| Standard Webhooks (`webhook-id`, `webhook-timestamp`, `webhook-signature`) | `webhook.NewStandard(webhook.StandardConfig{Secrets: …})` |
| Svix, Resend, Clerk (`svix-id`, `svix-timestamp`, `svix-signature`) | `webhook.NewStandard(webhook.StandardConfig{Secrets: …, HeaderPrefix: "svix-"})` |
| GitHub (`X-Hub-Signature-256: sha256=<hex>` over the body) | `webhook.NewHMAC(webhook.HMACConfig{Secrets: [][]byte{secret}, SignatureHeader: "X-Hub-Signature-256", SignaturePrefix: "sha256=", Encoding: webhook.Hex})` |
| Shopify (`X-Shopify-Hmac-Sha256: <base64>` over the body) | `webhook.NewHMAC(webhook.HMACConfig{Secrets: [][]byte{secret}, SignatureHeader: "X-Shopify-Hmac-Sha256"})` |
| Slack (`v0:<timestamp>:<body>`) | `NewHMAC` with `TimestampHeader: "X-Slack-Request-Timestamp"` and a custom `Signed` function ([example](../methods/webhook.md#HMACConfig)) |
| A scheme that doesn't fit, such as Stripe's `t=…,v1=…` header or public-key signatures | Implement `webhook.Verifier` (below) |

GitHub and Shopify sign no timestamp, so their verifiers have **no replay window**: a captured request stays valid. Prefer senders that sign one, and make handlers idempotent either way.

### Rotating a secret

List both secrets, deploy, switch the sender to the new one, then remove the old one:

```go
webhook.StandardConfig{Secrets: []string{newSecret, oldSecret}}
```

### Your own verifier

```go
// stripeVerifier checks Stripe-Signature: t=<unix>,v1=<hex HMAC-SHA256 of "t.body">.
type stripeVerifier struct{ secret []byte }

func (v stripeVerifier) Verify(_ context.Context, header http.Header, body []byte) error {
	var ts string
	var sigs [][]byte
	for part := range strings.SplitSeq(header.Get("Stripe-Signature"), ",") {
		k, val, _ := strings.Cut(part, "=")
		switch k {
		case "t":
			ts = val
		case "v1":
			if sig, err := hex.DecodeString(val); err == nil {
				sigs = append(sigs, sig)
			}
		}
	}
	seconds, err := strconv.ParseInt(ts, 10, 64)
	if err != nil || time.Since(time.Unix(seconds, 0)).Abs() > webhook.DefaultTolerance {
		return webhook.ErrInvalidSignature
	}
	mac := hmac.New(sha256.New, v.secret)
	mac.Write([]byte(ts + "."))
	mac.Write(body)
	want, valid := mac.Sum(nil), false
	for _, sig := range sigs {
		if hmac.Equal(sig, want) {
			valid = true
		}
	}
	if !valid {
		return webhook.ErrInvalidSignature
	}
	return nil
}
```

Return an error wrapping `webhook.ErrInvalidSignature` for requests that aren't authentic, so the guard answers 401; any other error becomes a 500.

### Replays and retries

Verification proves who sent a request, not that it's the first time: providers retry with the same delivery ID, and a captured request can be replayed within the 5-minute window. The guard doesn't remember IDs; make the handler idempotent. The simplest way is to store the delivery ID in the same transaction as the change:

```sql
INSERT INTO webhook_deliveries (id, received_at) VALUES ($1, now()) ON CONFLICT DO NOTHING
```

and skip the change when no row was inserted, answering 2xx so the sender stops retrying.

**What it doesn't do.** It doesn't protect a leaked secret (rotate it), check that the event makes sense for your data, or stop a sender from delivering events out of order: use the event's own timestamps or versions when order matters.

## External identity providers (JWT)

When a provider signs your users in (a mobile app with Auth0, a SPA with Clerk), your API receives its access tokens. `gorbital.dev/modules/jwt` verifies them and puts the caller in the context as an `actor`, so `guard.Permission`, rate limits by user and audit work as with gorbital's own sessions.

```bash
go get gorbital.dev/modules/jwt
```

```go
idp, err := jwt.New(ctx, jwt.Config{
	Issuer:    "https://example.eu.auth0.com/",
	Audiences: []string{"https://api.example.com"},
	JWKSURL:   "https://example.eu.auth0.com/.well-known/jwks.json",
})
if err != nil {
	return err // bad configuration, or the provider's keys can't be fetched
}
handler := httpx.Chain(mux, httpx.Recover(logger), httpx.RequestID(), idp.Middleware(logger))
```

In an app on `gorbital.Main`, one line does the same: `gorbital.WithAuth(idp)`.

| Request | Result |
|---|---|
| `Authorization: Bearer <valid JWT>` | Actor: a user whose ID is `sub` and whose permissions come from the `permissions` claim |
| No bearer token, another scheme, or a bearer token that isn't a JWT (such as an API key) | Continues anonymously: routes that need a caller answer `401 unauthenticated` |
| A JWT that is expired, tampered with, for another audience or issuer, or signed with a key or algorithm that isn't allowed | `401 invalid_token` with `WWW-Authenticate: Bearer error="invalid_token"`: the client should get a new token |
| The provider's keys can't be fetched and the token's key isn't cached | `503 auth_unavailable`: retry later |

### Providers

Check each value in your provider's dashboard; these are the usual shapes.

| Provider | `Issuer` | `JWKSURL` | Audience | Permissions |
|---|---|---|---|---|
| Auth0 | `https://<tenant>.<region>.auth0.com/` (with the slash) | `<issuer>.well-known/jwks.json` | `Audiences`: the API identifier | `permissions` (enable RBAC and "Add Permissions in the Access Token") |
| Clerk | `https://<your frontend API host>` | `<issuer>/.well-known/jwks.json` | `AudienceClaim: "azp"`, `Audiences`: your app's origins | Custom claims via a session token template, or `ActorFrom` |
| Supabase | `https://<ref>.supabase.co/auth/v1` | `<issuer>/.well-known/jwks.json` | `Audiences: []string{"authenticated"}` | `ActorFrom` from `app_metadata` (`Claims.Decode`) |
| Firebase | `https://securetoken.google.com/<project-id>` | `https://www.googleapis.com/service_accounts/v1/jwk/securetoken@system.gserviceaccount.com` | `Audiences`: the project ID | Custom claims, via `ActorFrom` |
| Amazon Cognito (access tokens) | `https://cognito-idp.<region>.amazonaws.com/<user-pool-id>` | `<issuer>/.well-known/jwks.json` | `AudienceClaim: "client_id"`, `Audiences`: the app client IDs | `PermissionsClaim: "scope"`, or `cognito:groups` via `ActorFrom` |

`Algorithms` defaults to RS256, ES256 and EdDSA; set it to exactly what your provider uses when you know it. Supabase projects still on the legacy shared JWT secret use `Algorithms: []string{"HS256"}` with `jwt.WithHMACSecret(secret)` and no `JWKSURL`; prefer its asymmetric keys, since anyone with the secret can issue tokens.

### Mapping claims to the actor

The default actor is a user with ID `sub` and the permissions in `PermissionsClaim`. Use `ActorFrom` to map provider permission names to your module's, recognise machine tokens, or set the organisation:

```go
jwt.Config{
	// …
	ActorFrom: func(c jwt.Claims) (actor.Actor, error) {
		if c.String("token_use") != "access" { // Cognito: refuse ID tokens
			return actor.Actor{}, errors.New("not an access token")
		}
		a := actor.Actor{Kind: actor.KindUser, ID: c.Subject, OrgID: c.String("org_id")}
		if c.String("gty") == "client-credentials" { // Auth0 machine-to-machine
			a.Kind = actor.KindService
		}
		for _, scope := range c.Strings("scope") {
			if scope == "read:books" {
				a.Permissions = append(a.Permissions, "books.book.read")
			}
		}
		return a, nil
	},
}
```

An error from `ActorFrom` refuses the token with 401; so does an actor that isn't a user or service, or has no ID.

### Keys, caching and outages

| Situation | Behaviour |
|---|---|
| Start | `jwt.New` fetches the keys; an unreachable provider or a key set without usable keys is an error, so a mistyped URL fails at deploy |
| Normal traffic | Keys come from memory, cached as long as the provider's `Cache-Control: max-age` says, between 5 minutes and 24 hours |
| The provider rotates keys | The first token naming the new `kid` fetches the key set again; at most one fetch every 30 seconds, shared by every waiting request, so random `kid`s can't cause a storm |
| The provider is down | Cached keys keep working for up to 24 hours past their cache age; tokens with a key that isn't cached get 503 |

Only public signing keys are used: RSA of at least 2048 bits, ECDSA and Ed25519, and only with an algorithm that fits the key. `alg: none` is never accepted, and keys embedded in a token (`jwk`, `jku`, `x5u`) are ignored.

Outside HTTP middleware, such as for a WebSocket's first message, call `idp.Verify(ctx, token)`.

**What it doesn't do.** It doesn't sign users in, refresh tokens or revoke them: a token stays valid until `exp`, so keep access tokens short-lived at the provider. It doesn't know about gorbital sessions: `guard.RecentReauth` needs an `auth.Principal` and refuses JWT callers. It doesn't tell ID tokens from access tokens unless their audiences differ or `ActorFrom` checks a claim such as Cognito's `token_use`.

## Error codes

These codes are public API like every other ([Stability](stability.md)), and the [error code reference](../reference/error-codes.md) lists them with the rest. A Full app has the timeout, IP filter and webhook codes already; `modules/jwt`'s are marked there as belonging to a module an app adds.

| Code | Status | Meaning | Layer |
|---|---|---|---|
| `request_timeout` | 503 | The request took longer than the server allows; retry later, or narrow the request | `httpx/timeout` |
| `ip_not_allowed` | 403 | Requests from the client's network address aren't allowed on this endpoint | `httpx/ipfilter` |
| `invalid_webhook_signature` | 401 | The webhook signature is missing, invalid or too old | `guard.Webhook` |
| `request_too_large` | 413 | The webhook body is larger than the route allows | `guard.Webhook` |
| `invalid_token` | 401 | The bearer JWT is invalid or expired; get a new token | `modules/jwt` |
| `auth_unavailable` | 503 | The identity provider's keys can't be fetched; retry shortly | `modules/jwt` |
