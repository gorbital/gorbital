# Upgrading a v0.1 app

An app generated by `orb v0.1.0`, with a resource of its own, a rule added to the generated sign-in code and middleware of its own, moved to the v0.2 layout with one command. Every output on this page is from that run.

Moving is opt-in. A v0.1 app builds and passes its tests against the v0.2 library with `go get` and no code changes ([upgrade notes](../../guides/upgrade-notes.md#upgrading-to-v020)), and `orb upgrade` keeps merging v0.1-layout fixes into it. Move when you want the library to own the parts you never wanted to maintain: sign-in, `/ops`, client flags, email events, organisations and the wiring.

## The app

```bash
orb new shop-api --preset full          # orb v0.1.0
orb gen resource Note title:string:unique body:text
```

Then three changes by hand, the kind a real app has:

<div class="steps">

1. **A rule in the generated sign-in module**, in `internal/modules/auth/usecase/register.go`:

   ```go
   // Addresses of domains we ban never get an account (a rule of ours).
   if strings.HasSuffix(normalized, "@blocked.example") {
       return authlib.ErrInvalidEmail
   }
   ```

2. **Middleware of its own**, `internal/app/client_version.go`, refusing mobile clients older than `2.0`, added to the stack in `internal/app/routes.go` after the body limit.

3. **A hand-written module** is just as good an example; this app uses the generated `notes` and the example `projects` module.

</div>

## Before the move

The move needs the app on this release's v0.1 templates, so the two versions of every generated file are known:

```bash
orb upgrade          # merges this release's v0.1-layout templates, on a branch
go test ./...
git merge orb-upgrade/<version>
```

## The move

```bash
orb upgrade --layout v0.2
```

It writes the files, rewrites `internal/modules/modules.gen.go`, runs `go mod tidy`, `gofmt` and `go build ./...`, exports `api/` again and records `api/surface.json`. Nothing is committed:

```text
  next:
        go test ./...   (database tests need orb dev or docker compose up -d --wait)
        git diff api/openapi.json   (re-exported: every route gains x-gorbital-guards, and the /ops instance example takes this app's name)
        git diff api/surface.json api/openapi.baseline.json   (rewritten: the built-in modules' names are the library's now, so only this app's are recorded)
        orb doctor
        git add -A && git commit -m 'Move to the v0.2 layout'

  nothing is committed: git diff shows every change, git restore . undoes them, and UPGRADE-v0.2.md says what was done
```

`git diff --stat`: 197 files changed, 1428 insertions, 19324 deletions. The deletions are the code the library now runs.

## The rule in sign-in, afterwards

`internal/modules/auth` is the app's copy of `authhttp` now, with the ban in `RegisterWithFields`, and `gorbital.lock` records where it came from. The report named the hooks that could replace it. Doing that gives the module back to the library:

```go
auth := authhttp.New(authhttp.OnRegister(func(ctx context.Context, tx pgx.Tx, a authhttp.NewAccount) error {
	if strings.HasSuffix(a.User.Email, "@blocked.example") {
		return authhttp.Refuse("registration_closed", "this domain can't register")
	}
	return nil
}))
```

Then delete `internal/modules/auth`, drop its `ejected` entry from `gorbital.lock` and import `gorbital.dev/gorbital/authhttp` in `main.go` again ([The code in your repo](../../guides/the-code-in-your-repo.md#apps-that-came-from-somewhere-else)). Keep the copy if the change is bigger than a hook: `orb doctor` tells you when the library's version of the module changes.

## What was left

`_upgrade-v0.1/internal/app/notes_test.go`: the HTTP test `orb gen resource` wrote for the old composition root. Port it to the module (`internal/modules/notes/notes_test.go` with `gorbitaltest`, as a new app's module tests are written) and delete the directory, which the go command ignores until then.

## Going back

`git restore . && git clean -fd` before you commit, `git revert <commit>` after. The v0.1 layout keeps working, and `orb upgrade` keeps merging its templates.
