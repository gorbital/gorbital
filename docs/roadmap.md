# gorbital Roadmap

**Status:** Accepted (2026-09-14) · **Replaces:** `scope-v1.md`

gorbital's work is planned in milestones, each named after its theme. Each one is usable on its own and has a definition of done. Nothing outside a milestone's scope starts without an accepted ADR.

## Releases

`v0.1.0`, published on 2026-09-17, is the first public release of the library (`gorbital.dev` and the modules under `gorbital.dev/modules/`) and of `orb` (`gorbital.dev/cli`), which are versioned together. Install `orb` with `go install gorbital.dev/cli/cmd/orb@latest`, or add the library with `go get gorbital.dev@latest`. It contains every milestone below marked done or built, and the Dev Portal phases built so far. Milestones are themes of work, not releases: during development they carried internal numbers (v0.1 to v1.4), which older decision records still use.

Further v0.x releases follow as work lands. In Go terms v0 carries no compatibility promise, but the compatibility checks (API listings, `api/surface.json`, the `/ops` OpenAPI baseline, `--json` golden files) already run to catch accidental breaks, and breaking changes are listed in the [changelog](../CHANGELOG.md) and the [upgrade notes](guides/upgrade-notes.md). `v1.0.0`, with the API freeze and the scaffold compatibility promise in force, comes only after the external security review signs off ([ADR-0015](adr/0015-public-api-and-stability-tiers.md), [stability](guides/stability.md)).

## Data and identity

**Status: done** (2026-09-15). What was built:

- **Database** (2026-09-14): `modules/postgres` with a traced pool, `DBTX`, `InTx`, error classification, goose migrations under an advisory lock, a readiness check, and `pgtest` against Docker PostgreSQL. Repositories use hand-written SQL ([ADR-0032](adr/0032-repository-sql.md)).
- **Runtime settings** (2026-09-14): `modules/settings` and core `config.Value[T]`: typed declarations, a PostgreSQL store with version checks, history and audit events, `LISTEN/NOTIFY` with periodic resync ([ADR-0031](adr/0031-runtime-settings.md)).
- **Background jobs** (2026-09-14): `modules/jobs` with a River client (context propagation, graceful stop), job definitions with runtime-editable configuration and schedules, a `Manager` for admin APIs, `AsyncSender` and River migrations ([ADR-0033](adr/0033-background-jobs.md)). `orb gen job`, interactive or with flags ([ADR-0035](adr/0035-interactive-cli.md)).
- **Golden app**: `examples/full-single` wiring PostgreSQL, settings and jobs, with `cmd/migrate`, `compose.yaml`, and `/ops/settings`, `/ops/jobs/*` and `/ops/queues`, first behind an interim `OPS_TOKEN`.
- **Audit log**: `modules/auditpg`, an append-only `audit_events` table with `Record` and transactional `RecordTx`, metadata redaction and size bounds, filtered and paginated `List`, and `GET /ops/audit`, `/ops/audit/{id}` (moved from operations and upgrades) ([ADR-0036](adr/0036-audit-storage.md)).
- **Email**: `modules/mail/smtp` and `modules/mail/resend`, core `mail.ErrRejected` and `mail.WithDefaults`, rejected sends cancelled by the mail worker, Mailpit in development, the sender as runtime settings, `GET /ops/mail` and `POST /ops/mail/test`, and `orb add mail` to choose or switch Resend or SMTP ([ADR-0037](adr/0037-email-setup-and-delivery.md)).
- **Authentication** (2026-09-15, [ADR-0038](adr/0038-authentication-v0-2.md)): `modules/auth` building blocks (argon2id, tokens and codes stored as hashes, session middleware and cookies, permission catalog, emails) and an app-owned `internal/modules/auth` with all four layers and `/v1/auth`: register, email codes, login with cookie or bearer token, logout and logout-all, sessions, password reset and change, account deletion, platform roles (`platform_admin`, `ops_viewer`) granted with `go run ./cmd/api grant-role`, and the `auth_cleanup` job. `OPS_TOKEN` was removed: `/ops/*` uses sessions and roles.
- **Example resource** (2026-09-15, [ADR-0039](adr/0039-resource-module-template.md)): `internal/modules/projects`, owned by the signed-in user, with its own table, keyset pagination through `page`, versioned `PATCH`, audit events, cross-owner isolation tests and an end-to-end test. It's the template for `orb gen resource`, which supports string, text and enum fields with unique and filter options, reproduces the module byte for byte, and is tested by generating other resources into a copy of the app.
- **Release tracking** (2026-09-15, [ADR-0040](adr/0040-release-tracking.md)): `modules/releases` records each instance's build with a heartbeat and clean-stop marking, derives releases and prunes old instances; `GET /ops/releases`, `/ops/releases/current` and `/ops/releases/instances` (moved from operations and upgrades).
- **`orb new --preset=full`** (2026-09-15, [ADR-0041](adr/0041-full-preset-generation.md)): templates generated from `examples/full-single` and checked byte for byte, `go.mod` derived from each golden app's, a leak check for repository paths, the database named after the app. A new Full app passes its own tests and accepts `orb gen resource` and `orb gen job`.
- **`orb gen migration`** (2026-09-15): an empty forward-only migration that sorts last, tested by adding a column to a generated resource's table in a new app.
- **Seed data** (2026-09-15, [ADR-0042](adr/0042-development-seed-data.md)): `cmd/seed` creates `admin@example.com` with `platform_admin`, a random password printed once, and three example projects, through the modules' use cases; development only and safe to rerun.
- **`orb dev` with Docker** (2026-09-15, [ADR-0028](adr/0028-local-development-environment.md)): `.env` from `.env.example`, Docker and port checks naming the `.env` line to change, `docker compose up -d --wait`, migrations (again when one changes) and seed data before the app starts; `--no-services`; `--observability` starts Grafana and points the app's OpenTelemetry export at it.
- **Moved out:** the Custom preset to operations and upgrades (later dropped), the tenancy prompt to organisations.

## Strong authentication

**Status: done** (2026-09-15). Threat model rows 14–16 reviewed and marked done; every method is covered by its integration tests. What was built:

- **Two-factor authentication** ([ADR-0043](adr/0043-two-factor-authentication.md)): TOTP (RFC 6238) in `modules/auth` with an AES-256-GCM `Keyring` from `AUTH_ENCRYPTION_KEYS` and `rotate-auth-keys`; 10 single-use recovery codes; a sign-in challenge (`POST /v1/auth/login` returns 202, `POST /v1/auth/login/mfa` finishes); replay protection across instances; `Catalog.RequireMFA` and core `actor.Require` with step-up permissions; `platform_admin` and `ops_viewer` require 2FA in every environment (403 `mfa_required`); `reset-mfa` for lost devices; seed data that enrolls the administrator; `orb dev` writing a development key to `.env`.
- **Passkeys** ([ADR-0044](adr/0044-passkeys.md)): `modules/auth/passkey` wrapping `go-webauthn`, with a `passkeytest` software authenticator; passwordless sign-in and passkeys as a second factor; up to 10 per account; single-use ceremonies, user verification and clone detection; `WEBAUTHN_*` configuration with localhost in development; `/.well-known/apple-app-site-association` and `assetlinks.json` for iOS and Android apps; a QR code image in authenticator app setup. After review: changes to sign-in methods need the password once a session's second factor is 10 minutes old, and a passkey can confirm account deletion, turning off the authenticator app and replacing recovery codes.
- **Provider setup** ([ADR-0045](adr/0045-sign-in-provider-setup.md)): `AUTH_PROVIDERS.md` in every Full app, a `.env.example` block per method, a **Sign-in methods** block at start, `go run ./cmd/api auth-providers` and `GET /ops/auth/providers`.
- **Google and Apple sign-in** ([ADR-0046](adr/0046-google-and-apple-sign-in.md)): `modules/auth/social` on `x/oauth2` and `go-oidc`, with a `socialtest` fake provider; an API-hosted web flow with state bound to a cookie, PKCE and nonce; native ID-token sign-in with server nonces; automatic linking on a verified email, removing an unverified account's password; the second factor still required; identities, Apple token revocation and notifications; `APP_PUBLIC_URL`.
- **CLI look** ([ADR-0035](adr/0035-interactive-cli.md), notes from this milestone): prompts in the gorbital theme ([theme](brand/theme.md)); `orb new` asks one question at a time, folds each answer into one line, and prints a log of finished steps ending with `next:`.
- **Follow-ups outside the definition of done:** sign-in against real Google and Apple accounts (needs the maintainer's credentials), and Apple token revocation with retries.

APIs only: the Dev Portal and Observability Portal in gorbital-dashboards stay on mock data, and no dev console UI was built. Each feature landed in the library, both Full golden apps and their templates, with an upgrade note. What was built:

- **Per-organisation settings** (2026-09-16, [ADR-0056](adr/0056-per-organisation-settings.md), [guide](guides/runtime-settings.md)): settings declared `settings.OrgOverridable()` take a value per organisation, which `Setting.Get(ctx)` returns from memory when the actor acts in that organisation; the store gains `ListForOrg`, `GetForOrg`, `SetForOrg`, `ResetForOrg`, `HistoryForOrg` and `Overrides`, with versions, reasons, history and `settings.value.changed` audit events carrying the organisation. Multi-tenant apps: `/v1/orgs/{orgId}/settings` (list, get, set, reset, history) for members (`orgs.settings.read`) and owners and admins (`orgs.settings.write`), with `orgs.invitation_ttl` as the example, values purged with the organisation through foreign keys. Both Full apps: `GET /ops/settings/{key}/overrides`, `org_overridable` in setting responses, and `TestSecuritySettingsArentOrgOverridable` keeping sign-in, rate limit, retention, maintenance, mail and link-target settings platform-only.
- **Feature flags** (2026-09-16, [ADR-0057](adr/0057-feature-flags.md), [guide](guides/feature-flags.md)): new `modules/flags`. Flags are declared in Go (`flags.Bool(reg, key, flags.Describe, flags.Group, flags.Client, flags.DefaultOn)`); a flag's state is `enabled`, `default`, organisation and user allow and deny lists (at most 1,000 IDs each) and an optional rollout percentage. `Enabled(ctx)` reads memory: disabled → false; organisation deny/allow (when the actor acts in an organisation); user deny/allow; percentage by SHA-256 bucket of flag key and subject (the organisation, else the actor; anonymous callers only follow 0 and 100); default. States are stored only when changed (`flags_states`, `flags_history`), changed through `/ops/flags` with a version and a required reason, audited (`flags.flag.changed`, `flags.flag.reset`) and applied on every instance through `LISTEN/NOTIFY` with a 5-minute resync. Both Full apps: `/ops/flags` (`ops.flags.read`, `ops.flags.write`), `GET /v1/flags` for signed-in clients (flags declared `Client()` only; permission `flags.flag.read`, which the `user` role gives every user, so API keys need it in their scopes), example flag `example.ping_time` (adds `server_time` to `GET /v1/ping`), `flags_history` retention; multi-tenant apps also `GET /v1/orgs/{orgId}/flags` for members.
- **API keys and service accounts** (2026-09-16, [ADR-0058](adr/0058-api-keys-and-service-accounts.md), [guide](guides/api-keys.md)): `gbk_<lookup>_<secret>` keys (128-bit lookup ID, 256-bit secret) stored as SHA-256 and compared in constant time, shown once, with a required expiry (`auth.api_key_max_ttl`, 90 days, at most a year), scopes and last use; `auth.Middleware` routes them through `WithAPIKeys`, never as sessions; personal keys (`/v1/auth/api-keys`, password or recent 2FA required), platform service accounts (`/ops/service-accounts`, `ops.service_accounts.read|write`) and, in multi-tenant apps, organisation service accounts (`/v1/orgs/{orgId}/service-accounts`, owners and admins, `orgs.service_accounts.manage`) that act only in their organisation through `orgs.RequireMember`. Keys never get permissions of roles that require 2FA (so `/ops` stays human-only), can't manage accounts, sessions or keys (`session_required`), are revoked by disabling a service account, deleting the account, resetting the password or claiming the address, and failed keys are limited per client network (`auth.api_key_failures_per_minute`). Responses showing a new key are `Cache-Control: no-store`, which the idempotency middleware never stores. `auth_cleanup` records `auth.api_key.expired` and removes keys 30 days after expiry or revocation. Scopes cover every operation: a `user` role every user holds grants the permissions of what any signed-in user may do (user-scoped resources, creating and listing organisations, reading client flags), so a read-only key is read-only; joining and leaving organisations need a session.
- **GitHub sign-in** (2026-09-16, [ADR-0059](adr/0059-github-sign-in.md), [guide](sign-in/github.md)): `social.NewGitHub` adds a provider without OpenID Connect to `modules/auth/social`: authorization code with state and PKCE S256, scopes `read:user user:email`, then `GET /user` and `GET /user/emails`, taking the primary address only when GitHub verified it (no-reply addresses count as none), subject = numeric user ID; `socialtest` gains a fake GitHub. Both Full apps: `GET /v1/auth/github/start` and `/callback`, `GITHUB_CLIENT_ID`/`GITHUB_CLIENT_SECRET`, the `github` status line; GitHub is never authoritative, so it never links an existing account (`social_link_required`) and its accounts start unverified (kept by `auth_cleanup`, claimed by whoever proves the address by email). Signed-in users link it with `POST /v1/auth/github/link` (password; the flow is bound to the browser by the `__Host-oauth` cookie and to the session, which must still be active at the callback). Browser sign-ins without `return_to` now end at `AUTH_DEFAULT_RETURN_TO`, required in production with a web sign-in provider (they used to end at the API docs, which answer 404 there).
- **Idempotency keys** (2026-09-16, [ADR-0060](adr/0060-idempotency-keys.md), [guide](guides/idempotency.md)): new `modules/idempotency` (PostgreSQL store and HTTP middleware). Signed-in POST and PATCH requests with `Idempotency-Key` claim the key atomically per caller (actor kind and ID, hashed with the key), fingerprinted by method, path, query and body; a retry replays the stored status, headers and body with `Idempotent-Replayed: true`; a different request with the key gets 422 `idempotency_key_reused`, a concurrent one 409 `idempotency_in_progress`. Server errors, panics, 401/403/408/429, `Set-Cookie` responses, `Cache-Control: no-store` responses, bodies over 1 MiB and `idempotency.DontStore` release the key; stale locks expire after 5 minutes. Both Full apps skip `/v1/auth/*`, document the header on every other POST and PATCH operation, and add setting `idempotency.retention` (24 h), job `idempotency_cleanup` and the `idempotency_keys` retention policy.
- **Row-level security option** (2026-09-16, [ADR-0061](adr/0061-row-level-security.md), [guide](guides/row-level-security.md)): every pool from `postgres.Open` sets `gorbital.org_id` on each connection from the acquiring context (the actor's `OrgID` after `orgs.RequireMember`, or `postgres.WithOrg`), remembered per connection so an unchanged acquire sends nothing; `postgres.WithoutRowLevelSecurity(ctx, reason)` bypasses for system paths, logged once per context and named on spans, and `postgres.Migrate` uses it; `postgres.CheckRowLevelSecurity` reports bypassing roles and unforced or unprotected tables. `orb add rls` (multi-tenant apps) copies `db/row_level_security.sql` into a migration that forces row-level security with an `org_isolation` policy on every `org_id NOT NULL` table except `org_members` and `org_invitations`, and records `rls: true` in `gorbital.yaml` and the lock (round-tripped by `orb upgrade`); `orb gen resource --scope org` then adds the policy to new tables. Both Full apps warn at startup and in `migrate --status`/`orb doctor` when the role bypasses the policies; full-multi's tests run the app as a role without bypass (`GORBITAL_TEST_RLS=1` turns the policies on for the whole suite).
- **Resend bounce and complaint webhooks** (2026-09-16, [ADR-0062](adr/0062-resend-webhooks-and-suppression-list.md), [guide](guides/email.md#bounces-complaints-and-the-suppression-list)): `resend.VerifyWebhook` checks Resend's Svix signatures (HMAC-SHA256, constant-time comparison, 5-minute tolerance) and `resend.ParseWebhookEvent` reads bounces and complaints; core `mail` gains `SuppressionList`, `WithSuppressionList` and `ErrSuppressed`; new `modules/mail/suppressionpg` stores the list and applied delivery IDs. Both Full apps cancel email to suppressed addresses, receive `POST /v1/webhooks/resend` (on only with `RESEND_WEBHOOK_SECRET`; hard bounces and complaints suppress, replays refused by `svix-id`), and add `GET /ops/mail/suppressions` and `DELETE /ops/mail/suppressions/{id}` (new `ops.mail.write`, reason required, audited).
- **Prometheus `/metrics` option** (2026-09-16, [ADR-0063](adr/0063-prometheus-metrics.md), [guide](guides/production.md#prometheus-metrics)): `modules/telemetry` gains `WithPrometheus`, `MetricsHandler`, `WithRuntimeMetrics` and `RecordRoute`; `modules/postgres` gains `WithMeterProvider` (pool metrics). All three golden apps serve `GET /metrics` on a separate `METRICS_ADDR` listener, off by default and refused on the API's port, with no client-controlled labels. Full apps' spans and HTTP metrics now carry the matched route pattern.
- **Live observability and incident reports** (2026-09-16, [ADR-0064](adr/0064-live-observability-and-incidents.md), [guide](guides/observability.md)): new `modules/observability`. Every instance counts its HTTP requests per minute, method and route pattern (requests, 4xx, 5xx, a 35-bucket latency histogram; never paths or query strings; at most 500 series and 11 minutes in memory) and upserts them into `observability_minutes` every 15 seconds; one grouping-sets query adds up every instance. Both Full apps serve `GET /ops/observability/overview` and `/routes` (request rate, error rate, p50/p95/p99 estimated within one bucket's width, per instance, top routes, per minute) and `/stream` (Server-Sent Events every 5 s, 10 minutes, 2 per user and 20 per instance, session and permission rechecked before each event, ended on shutdown). Incidents (`sev1`–`sev4`, investigating → identified → monitoring → resolved, timeline updates) through `/ops/incidents`, audited as `ops.incident.opened|updated|resolved`; `GET /ops/incidents/{id}/report` as JSON or Markdown with requests, audit events (without IPs, user agents or metadata) and releases of the window, each section behind its own read permission. The `incidents_detect` job (every minute) opens one automatic incident when the 5xx rate over `incidents.detection_window` exceeds `incidents.error_rate_threshold` with `incidents.min_requests`, notes recovery and relapse, never resolves; an advisory lock and a partial unique index keep it to one across instances. `observability_cleanup` enforces `observability.retention` (24 h).
- **Local dev console APIs** (2026-09-16, [ADR-0065](adr/0065-local-dev-console-apis.md), [guide](guides/dev-console.md)): new `modules/devconsole` serves development-only `/_dev/` JSON APIs in front of the middleware chain, only when `APP_ENV=development` and `DEV_CONSOLE_TOKEN` is set (production refuses the token). Every request needs a `Host` of exactly `localhost`, `127.0.0.1` or `[::1]` with the app's port (DNS rebinding), a loopback peer and `Authorization: Bearer` compared in constant time; no CORS, `Cache-Control: no-store`. All three golden apps serve `/_dev/app`, `/_dev/routes`, `/_dev/config` (variables `LoadConfig` read, secrets as set/unset only), `/_dev/requests` and `/_dev/logs` (bounded ring buffers, via `Collector.Subscribe` and the new `telemetry.WithLogTee`) with SSE streams, and `/_dev/openapi.json`; Full apps add `/_dev/mail` (Mailpit), `/_dev/migrations` and `/_dev/jobs`. `orb dev` generates a 256-bit token per run, passes it in the app's environment only and prints it. No console UI is built on them yet.
