# ADR-0029: Threat model: framework, CLI and ecosystem

**Status:** Accepted (2026-09-14) · **Amended by:** ADR-0036 (audit metadata controls), ADR-0053 (internal security review: corrected rows, new rows 33 to 39, review status)

## Context

gorbital generates authentication, handles secrets, installs third-party recipes, runs on developer machines and publishes packages under a vanity import path. The threat model must cover the framework itself, not only apps built with it. This is an architecture-level model; specialist review and penetration testing are still required before 1.0.

## Assets

Developer machines (SSH keys, cloud and GitHub credentials), application source code, generated authentication code, end-user data in generated apps, the `gorbital.dev` domain and DNS, the GitHub organisation and release pipeline, the module index.

## Trust boundaries

CLI ↔ Go module proxy; recipe → owned code; `gorbital.dev` → `go-import` resolution; localhost dev services; CI workflows; app ↔ identity providers; tenant ↔ tenant; public API ↔ ops API.

| 35 | Invitation email abuse: spam or phishing sent from the app's domain through organisations and invitations | A verified address to create organisations and to invite; 20 invitations per organisation per hour; a per-user limit across organisations (`orgs.user_invitations_per_hour`); at most `orgs.max_owned` organisations per user | v1.0 |
| 36 | Account takeover through pre-registration or provider linking: registering someone's address before them, or signing in with a provider account for an address the provider doesn't manage | A contested registration keeps no password; proving the address (code, reset, provider link) ends sessions and removes passkeys, authenticator app, recovery codes and identities added before; automatic linking only for provider-authoritative emails; accounts a provider creates for other addresses stay unverified until proven by email | v1.0 |
| 37 | Unverified accounts used as a foothold: holding an address, a role or an organisation before the owner verifies | Unverified accounts can't sign in with a password or passkey (an account a provider created signs in only with that identity, which proving the address by email removes); deleted after `auth.unverified_account_ttl` (7 days); roles granted only to verified accounts; organisations and invitations need a verified address | v1.0 |
| 38 | Insecure production configuration: a deployment running with development defaults, public API documentation aiding reconnaissance, plain-http origins trusted | `APP_ENV` required at start; `/docs` and the OpenAPI document switched together and off by default in production; `APP_CORS_ORIGINS` https-only in production and parsed strictly everywhere | v1.0 |
| 39 | Denial of service through observability, health and ops endpoints: metric cardinality from `Host` headers, readiness floods draining the database pool, slow audit queries, unbounded hashing or test emails | `Host`-derived attributes dropped from metrics; readiness checks shared and reused for 1 s; audit listing and stats stop after 5 s; password hashing waits at most 5 s for a slot; 5 test emails an hour per operator | v1.0 |
| 40 | Organisation admins weakening security through their organisation's settings, or reading or changing another organisation's | Only settings declared `OrgOverridable` accept organisation values, within the platform's bounds, validation and reason requirement; the apps' `TestSecuritySettingsArentOrgOverridable` fails for sign-in, rate limit, retention, maintenance, mail and link-target settings; every organisation settings route starts with `orgs.RequireMember` (404 `org_not_found` to non-members); changes need `orgs.settings.write` (owner, admin), are versioned, kept in history and audited with the organisation; values are purged with the organisation ([ADR-0056](0056-per-organisation-settings.md)) | v1.1 |
| 41 | Idempotency keys replaying one caller's response to another, running a request twice under retries or races, or keeping secrets and personal data in stored responses | Keys scoped to the authenticated actor (kind and ID) and hashed with it; anonymous callers ignored; one-statement atomic claim with a lock token; fingerprint of method, target and body; `/v1/auth/*`, `Set-Cookie` responses and `DontStore` responses never stored; bounded retention (1 h to 7 days) and hourly cleanup; the table isn't exposed through `/ops` ([ADR-0060](0060-idempotency-keys.md)) | v1.1 |
| 42 | Forged or replayed provider webhooks suppressing a user's address (denying them password resets and codes) or flooding the suppression list; the list leaking addresses | Resend's Svix HMAC-SHA256 signature over ID, timestamp and raw body, every signature compared in constant time; 5-minute timestamp tolerance; applied `svix-id`s stored in the same transaction as the suppressions, so a replay changes nothing; endpoint 404 without `RESEND_WEBHOOK_SECRET`; 256 KiB body limit; malformed secret refused at start without being printed. | 43 | Metrics endpoint exposing service internals (routes, load, error rates, runtime) to the internet, or flooded with client-chosen label values to hide real series | Off by default; a separate listener serving only `GET /metrics`; `METRICS_ADDR` on the API's port refused at start; private binding and per-instance scraping documented; attributes limited to route patterns, normalised methods and status codes (`Host`, paths, queries, user agents, forwarded addresses and trace headers never become labels); scrape concurrency and time bounded ([ADR-0063](0063-prometheus-metrics.md)) | v1.1 |

## Residual risk

Owner: project maintainer. Each accepted risk is recorded here with a review date. An external security review of authentication, sessions, tenancy and the generator is required before 1.0; an internal review came first ([ADR-0053](0053-internal-security-review.md), [report](../security/2026-09-internal-review.md)).

| Accepted (2026-09-16) | Threat | Reason | Review |
|---|---|---|---|
| `/ops/releases` lists instance host names | 31 | Operator-only with 2FA; identifies instances during rollouts | Before 2.0, or when `/ops` gains a less trusted role |
| Run-now, retry, cancel, pause and resume have no history table; a failed audit write leaves only a log line | 29 | Transactional audit writes would let an audit outage block incident response | With the external review |
| `/version` shows the version, Go version and commit | 38 | Public by design for release tracking; can be blocked at the load balancer | With the external review |
| `go 1.26.0` directive kept, below the release with every `os.Root` fix | 3 | ADR-0015 sets the minimum Go version; `orb` warns below 1.26.5, CI and releases use the latest patch | Each Go minor release |
| Response-time floor can be exceeded by a slow database, showing timing differences again | 12 | The floor covers normal load; per-address limits bound probing | With the external review |
| No per-recipient invitation limit | 35 | Per-user limits on verified accounts bound each attacker account | When invitation volume is observed in production |
| A request running longer than the 5-minute idempotency lock can run twice; stored responses keep personal data up to `idempotency.retention` | 41 | Longer locks would block legitimate retries after a crash; retention is bounded to 7 days and cleaned hourly | When long-running POST endpoints appear |
| Anyone holding `RESEND_WEBHOOK_SECRET` can suppress any address; `/ops` has no lookup by address | 42 | The secret is treated like the provider API key; operators remove suppressions with a reason; no addresses in URLs | With the external review |
| The metrics listener has no authentication | 43 | Network isolation is the control (off by default, refused on the API port, private binding documented); `METRICS_TOKEN` deferred | When a deployment needs scraping across a network boundary |

Reviewed against the code for v0.2's definition of done (rows 12, 13, 19, 23 and 24), 2026-09-15: each mitigation above is in place and tested. Notes from the review:

- Row 12: the breached-password hook is `authusecase.Config.PasswordChecker`. No checker is configured by default; an app chooses one (a local list, or a k-anonymity API) in `internal/app/module_auth.go`.
- Row 19: the auth use cases' log line for an email that couldn't be queued named its attribute `email`, which reads like an address; the value was always the email's kind (`verification_code`), never the address. It is now `email_kind`.
- Row 19: seed data (ADR-0042) prints the administrator's random password once to the developer's terminal, never to logs, files or the audit log, and refuses to run in production.
- Row 24: disabling requires a reason, a disabled job can't be run now (409) and leaves the schedule, and each change is in the job's history and audit log (`TestJobsThroughOps`).
