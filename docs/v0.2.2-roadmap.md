# v0.2.2 roadmap: choose what you get, and call it what you like

**Status:** Proposed (2026-09-21) · **Target release:** `v0.2.2` · **Branch:** `v0.2.2` · **Builds on:** [ADR-0015](adr/0015-public-api-and-stability-tiers.md), [ADR-0023](adr/0023-tenancy.md), [ADR-0048](adr/0048-organisations-v0-4.md), [ADR-0081](adr/0081-a-framework-you-import.md), [ADR-0082](adr/0082-routes-guards-and-middleware.md), [ADR-0083](adr/0083-modules-stack-migrations-and-ejection.md)

`v0.2.0` made gorbital a framework an app imports. `v0.2.2` makes it a framework an app *chooses*: sign-in you can turn down, tenancy you can name after your own business, and per-resource access rules the app owns.

```bash
orb new shop-api    --auth basic --scope merchant     # password sign-in, merchants own the data
orb new catalog-api --auth none  --scope none         # a public API, no users, no auth tables
orb new club-api    --auth basic --scope custom       # write your own membership rules from commit one
orb new saas-api    --auth full  --scope organisation # today's Full app, unchanged
```

```go
// The tenancy contract: the framework supplies the machinery, the app the vocabulary.
gorbital.WithScope(gorbital.Scope{
	Name:         "merchant",
	PathParam:    "merchantId",
	NotFoundCode: "merchant_not_found",
	ValidID:      merchants.ValidID,
	Roles:        merchants.Roles,
	Session:      postgres.WithScope("app.merchant_id"),
}, merchants.Authorizer(db))
```

```go
// Per-resource access is a policy the app writes, not a filter the generator assumes.
gorbital.Get(orders, "/{id}", h.getOrder, guard.Scope(PermOrderRead))
gorbital.Get(catalog, "/{id}", h.getItem, guard.Public())
```

## Current state

Assessed on 2026-09-21 against `main` (`93040dff`, `v0.2.1`), the golden apps and the CLI.

| Finding | Evidence | Consequence |
|---|---|---|
| The tenancy seam already exists, but is spelled *organisation* all the way down | `gorbital.OrgAuthorizer`, `Platform.SetOrgAuthorizer` (`gorbital/orgs.go`); `guard.OrgMember` (`gorbital/guard/guard.go`); `route.OrgIDParam = "orgId"`; `orgs.ParseID` called inside `authorizeOrg`; `postgres.OrgSetting = "gorbital.org_id"`; `Permission.OrgRoles`; `actor.Actor.OrgID` | v0.2.2 is **renaming and parameterising an existing interface**, not inventing one. **The actual problem, restated.** Apps cannot decline features they do not want, cannot call their tenant anything but an organisation, and cannot bring their own identity provider and still get tenancy. Everything needed to fix this is already in the code — as a fixed vocabulary instead of a parameter.

## Goals and non-goals

**Goals**

1. `orb new` creates an app with the sign-in and the tenancy the developer asked for, and **nothing else**: no unused routes in the OpenAPI document, no unused settings, no unused tables for a feature that is absent entirely.
2. Tenancy is a **contract the app fills in** — name, path parameter, ID format, roles, refusal code, database session — with organisations as the supplied implementation.
3. No built-in module requires another built-in module: organisations work with whatever authenticates the app, including an authenticator the app wrote itself.
4. Per-resource access is chosen and visible: `user`, `tenant`, `public` or `custom`, and a `custom` resource gets a policy file the developer owns, never a silent filter.
5. **Every v0.2 app keeps compiling and behaving identically.** Nothing in this release changes the HTTP contract, the problem codes, the permission names, the migration versions or the roles of an existing app, and `apicheck` records no changed or removed line. The one break is in the CLI, not the library: `orb eject` and `orb new --no-eject` are removed (ADR-0092), and the changelog and upgrade notes say so.
6. Every new public symbol is listed, documented with a runnable example, and covered by a test that proves isolation.

**Non-goals for v0.2.2**

- Turning a feature on *after* `orb new` (`orb add auth`, `orb add passkeys`). That needs out-of-order migrations; it is v0.4 (D7).
- Removing code for a disabled sign-in method from an ejected app (D6).
- `--auth external` as a supported profile, and tenancy read from an identity provider's claims. `modules/jwt` already satisfies `gorbital.Authenticator` for anyone who wires it by hand, and item 46 makes `/ops` work without gorbital's sign-in — but the profile, the claim-based scope authorizer, the configuration and the guides are **v0.4**.
- A second database, a scope stored anywhere but PostgreSQL, or scope resolution by subdomain.
- `.orb` drift detection, `orb explain`, `orb cyber`, `orb agent`, compliance profiles. Those follow; they all depend on the manifest this release writes.

## What the framework owns

The rule this release makes enforceable: **the framework owns mechanism, never policy.** Sign-in and tenancy split into three layers, and only the first is the framework's for good.

| Layer | Owner | What is in it | Ejectable |
|---|---|---|---|
| **1. Protocol and crypto** | **Library, permanently** | `gorbital.dev/modules/auth`: Argon2id parameters, session token generation and hashing, TOTP verification, API-key hashing, WebAuthn ceremonies, `crypto/subtle` comparisons, `Middleware`, `Catalog` | **Never** |
| **2. Flows** | The app | `gorbital/authhttp`, `gorbital/orgshttp`: registration, verification, password reset, login, account linking, invitations, member management, their SQL and their endpoints | Yes, by default |
| **3. Policy** | **The app, only** | Role names, which role holds which permission, what a tenant is, who may join one, what happens on sign-up | Not in the library at all |

Layer 1 is "help developers avoid boring security mistakes". Layer 3 is "never lock them into one business model". Layer 2 is where visibility was chosen over automatic fixes, and that trade only holds while 1 and 3 do.

Three consequences, each an item below:

1. **`orb eject` is removed, and with it the word** (items 36, 37). Since v0.2.1 `orb new` puts sign-in and organisations in the app, so there is nothing left to eject on demand: the command answers a question nobody has any more. The copying *machinery* stays — it is what `orb new`, `orb add orgs` and `orb upgrade --layout` run — but it becomes internal, and the documentation stops calling the app's own code "ejected". It is just the app's code. Layer 1 then needs no guard rule: with no command to take it out, `modules/auth` is in the library because there is no other place for it to be.
2. **The copied flows get a fix path, not just a warning** (item 40). `orb doctor` already reports that the library version of a copied module changed; v0.2.2 makes it name the security fixes and offer the patch, which is only possible because the copy has a recorded source version in `gorbital.lock`.
3. **A proof app with none of gorbital's identity code** (item 22). `byo-identity` has a hand-written `Authenticator`, a hand-written `ScopeAuthorizer` over its own tables, no `authhttp`, no `orgshttp`, no `modules/orgs` — and still gets guards, permissions, step-up, audit, row-level security and the generated isolation tests. It is the positioning statement as a CI job: if it stops building, the claim has stopped being true.

## Architecture

### The scope contract

One new value type and one interface in `gorbital.dev/gorbital`, replacing the fixed organisation vocabulary:

```go
// A Scope is the app's tenancy: what a tenant is called, how its IDs look,
// which roles it has, and how a request's tenant reaches the database.
// gorbital.dev/gorbital/orgshttp supplies one for organisations.
type Scope struct {
	// Name is the concept in lowercase singular, such as "organisation" or
	// "merchant". It names guards in logs and metrics and appears in the
	// OpenAPI descriptions the guards write.
	Name string
	// PathParam is the path parameter scope routes carry the ID in, such as
	// "orgId". Registration fails for a scope route whose path lacks it.
	PathParam string
	// NotFoundCode is the problem code that refuses a request for a scope
	// the actor is not a member of, such as "org_not_found". Unknown,
	// deleted, forbidden and malformed IDs are all refused with it and 404,
	// so IDs cannot be probed.
	NotFoundCode string
	// ValidID reports whether s is a well-formed ID. A malformed ID is
	// refused exactly like an unknown one, before the authorizer is asked.
	// Nil accepts any non-empty string.
	ValidID func(s string) bool
	// Roles are the scope's roles, most privileged first, with what each
	// grants. Permission.ScopeRoles names them.
	Roles []ScopeRole
	// Session carries the scope into the request's database connections for
	// row-level security. Nil leaves connections unscoped.
	Session func(ctx context.Context, id string) context.Context
}

// A ScopeAuthorizer decides whether the actor of a request may act in a
// scope. Its error semantics are unchanged from OrgAuthorizer: ErrNotFound
// for a scope the actor is not a member of, actor.ErrUnauthenticated,
// actor.ErrStepUpRequired, actor.ErrForbidden, anything else a 500.
type ScopeAuthorizer interface {
	AuthorizeScope(ctx context.Context, scopeID, permission string) (context.Context, error)
}

func WithScope(s Scope, a ScopeAuthorizer) Option        // the app sets it
func (p *Platform) SetScope(s Scope, a ScopeAuthorizer) error // a module sets it
func guard.Scope(permission string) gorbital.RouteOption // the guard
```

**What does not change.** `actor.Actor.OrgID` keeps its name: it is in the stable `actor` package, it is written into every audit event, and renaming a field costs every app more than the clarity is worth. Its documentation becomes "the scope the actor is acting in". `postgres.OrgSetting` keeps its value `gorbital.org_id`, because live row-level-security policies reference it; `postgres.WithScope(setting string)` is the general form and `WithOrg` is it applied to the default.

**Compatibility.** `OrgAuthorizer`, `SetOrgAuthorizer` and `guard.OrgMember` stay, deprecated, for all of v0.x. `SetOrgAuthorizer(a)` is `SetScope(orgshttp.DefaultScope(), adapt(a))`; `guard.OrgMember(p)` is `guard.Scope(p)`. `Permission.OrgRoles` stays alongside `ScopeRoles`; both set is an error naming the module.

### Sign-in profiles

`authhttp` gains one option, `Methods`, gating registration, settings, jobs, rate limiters and the OpenAPI document:

```go
const (
	MethodPassword        Method = "password"  // 13 operations; always on
	MethodOperators       Method = "operators" // 16; /ops/auth/users
	MethodTOTP            Method = "totp"      //  5
	MethodPasskeys        Method = "passkeys"  //  9
	MethodSocial          Method = "social"    // 12; Google, Apple, GitHub
	MethodAPIKeys         Method = "api_keys"  // 19; includes organisation service accounts
)

func Methods(m ...Method) Option // default: every method, i.e. v0.2 behaviour
```

| `--auth` | Authenticator | Operations (of 74) | Auth migrations |
|---|---|---:|---|
| `none` | none | 0 | none |
| `basic` | `authhttp.New(authhttp.Methods(MethodPassword, MethodOperators))` | 29 | all 8 |
| `full` | `authhttp.New()` | 74 | all 8 |

The counts are exact, from `grep -c 'OperationID: "'` over `gorbital/authhttp/internal/delivery/` at `v0.2.1`.

`basic` keeps all eight auth migrations (D7): the tables exist and are empty, so a later `orb add passkeys` is a wiring change, not a migration ordering problem. `none` has no auth module at all, so no auth migrations are ever written into the app.

### Tenancy profiles

| `--scope` | What the app gets | Legal with |
|---|---|---|
| `none` | no scope, no members, no scope columns | any `--auth` |
| `single` | one implicit scope; data belongs to users | `basic`, `full` |
| `<name>` (`organisation`, `merchant`, `restaurant`, …) | `orgshttp` mounted under the chosen vocabulary: members, roles, invitations, per-scope settings and flags | `basic`, `full` |
| `custom` | the membership tables and a `ScopeAuthorizer` stub; **no** `orgshttp` — the app writes its own membership rules from the first commit | `basic`, `full` |

`--tenancy single|multi` keeps working and maps to `--scope single` and `--scope organisation`.

Nine combinations are legal. `--auth none --scope single` is refused with a message: data owned by users needs users.

### How the templates do not multiply

The rule: **one tree, composed; a fixed number of byte-golden apps.**

1. One v0.2.2 template tree (`cli/internal/recipes/v0.2.2/`) replaces `v0.2/full` and `v0.2/full-multi`.
2. `cli/internal/recipes/v0.2.2/manifest.yaml` lists, for each template path, the features that must be on for it to be written — the only place feature-to-file mapping lives.
3. **The demonstration `projects` module is generated, not templated.** Measured on v0.2.1, `v0.2/full` and `v0.2/full-multi` share 62 paths and 36 of them differ; 25 are the `projects` module, differing only because the resource is user-owned in one and organisation-owned in the other — which is the distinction `orb gen resource --scope` already expresses (ADR-0091).
4. **The five API artefacts are produced, not templated.** `api/openapi.json`, `openapi.baseline.json`, `postman_collection.json`, `surface.json` and `llms.txt` are outputs of the app and account for 7 089 of the 7 700 differing lines. `orb new` runs `go run ./cmd/api openapi --dir api` after `go mod tidy`, as CI already does for the golden apps.
5. That leaves six templates carrying `⟦if⟧` blocks — `cmd/api/main.go.tmpl`, `.env.example.tmpl`, `compose.yaml.tmpl`, `README.md.tmpl`, `AGENTS.md.tmpl`, `gorbital.yaml.tmpl` — and nothing else.
6. Three golden apps stay byte-compared by `TestNewAppIsTheGoldenApp`: `examples/full-multi` (full + organisation), `examples/full-single` (full + single) and `examples/api-basic` (basic + none).
7. The other six combinations get a CI matrix that creates, builds, vets and tests them — not byte equality. Golden files are for shapes we document; the matrix is for shapes we support.

### Resource policies

`orb gen resource --scope` grows from `user|org` to `user|tenant|public|custom`:

- `user` — unchanged; `owner_id`, permission guards.
- `tenant` — today's `org`, under the app's scope name and path parameter.
- `public` — reads `guard.Public()`, writes permission-guarded; no owner column.
- `custom` — the repository takes a `Policy` the generator writes into the module as the app's own file, with `CanRead`, `CanWrite` and `Filter` returning `ErrNotImplemented` and a comment saying what each must decide. The generator adds **no** implicit tenant filter and the migration adds **no** tenant column. `orb doctor` lists custom-scope modules as "isolation is this module's own".

Every scope except `custom` also generates the isolation tests that exist today for `org`, under the app's own vocabulary.

## Decisions

| # | Decision | Rejected alternative |
|---|---|---|
| D1 | Scope is the framework's concept; organisations are the supplied implementation. `Org*` names stay as deprecated aliases for all of v0.x | A hard rename (breaks every v0.2 app and every ejected module) |
| D2 | The scope contract is a struct the app fills: name, path parameter, refusal code, ID validation, roles, database session | A `Tenant` interface with ten methods; string-keyed configuration |
| D3 | `actor.Actor.OrgID` and `postgres.OrgSetting` keep their names and values | Renaming them; it would rewrite every audit row's meaning and break live RLS policies |
| D4 | `orgshttp.Module` takes an interface for what it needs from sign-in, not `*authhttp.Authenticator`. It is the seam, not a feature: nothing in v0.2.2 uses it besides the tests, and it is what makes external identity a v0.4 packaging job rather than a refactor | Leaving the concrete dependency, which contradicts the ownership rule and would make v0.4 a breaking change |
| D5 | Sign-in methods are a construction option with every method on by default; `MethodPassword` cannot be turned off while `authhttp` is mounted | A build tag per method; separate `authbasic`/`authfull` packages |
| D6 | A disabled method's **code** still ships in an ejected app; only its routes, settings, jobs, limiters and schema documentation are gated | Pruning files at eject time — the delivery, use-case and port layers are interlinked, so pruning would not compile |
| D7 | A profile's migrations are decided once, at `orb new`. Turning a method on later is v0.4 and needs `goose` out-of-order support, an ADR and a rollback story | Gating migrations per method now and discovering the ordering failure in a user's production database |
| D8 | Nine legal combinations; three byte-golden apps; a build-and-test matrix for the rest | Sixteen golden apps; or shipping combinations nothing builds in CI |
| D9 | Eject stays the default for every profile. *Resolved 2026-09-21:* if the framework never owns sign-in's business logic, ejecting it is the consistent choice, not a compromise | Making `basic` default to `--no-eject` (inconsistent, and it hides the code the user asked to see) |
| D10 | `gorbital.yaml` records `auth`, `scope`, `scopeName` and `methods`; `orb doctor` reads them | Inferring the profile from the code each time |
| D11 | Three stability layers (above), recorded as tiers in ADR-0015. Layer 1 is in the library and no command moves it | Treating all of sign-in as one blob |
| D15 | **`orb eject` is removed** (2026-09-21). `orb new` already writes sign-in and organisations into the app, so an on-demand command is redundant. The copy planner stays as internal machinery for `orb new`, `orb add orgs` and `orb upgrade --layout`. `--no-eject` goes with it: one shape, not two. `opshttp`, `flagshttp` and `mailevents` become library-only — they are plumbing, not business rules, and nothing in the ownership rule asks for them to be copied | Keeping a command whose only remaining users are people undoing a default; keeping `--no-eject`, which makes every guide say "unless you passed --no-eject" |
| D12 | Showcase applications move to their own repository, `gorbital/examples`, tagged in lockstep with the library. The **golden apps stay** — `examples/minimal`, `examples/full-single`, `examples/full-multi` and `examples/v0.1/*` generate `cli/internal/recipes/*` and are byte-compared in CI, so they are source, not documentation | Moving all of `examples/` (would break template generation); leaving 1 637 files of documentation apps in the library repository |
| D13 | The move preserves history with `git subtree split`, and the showcase apps switch from relative `replace` directives to the published module versions | A fresh repository with no history; keeping `replace` paths that only work inside a monorepo |
| D14 | External identity is out of v0.2.2 (2026-09-21). `modules/jwt` ships unchanged and still works for anyone who wires it themselves; the `--auth external` profile, claim-based tenancy and their guides are v0.4 | Carrying a whole phase for a mode no user has asked for yet, while the tenancy contract is still new |

New ADRs: **0088** *Scope: tenancy as a contract* (D1–D4), **0089** *Sign-in profiles* (D5–D7, D14), **0090** *Composing presets* (D8, D10), **0091** *Resource access policies*, **0092** *What the framework owns* (D11, D15), **0093** *The examples repository* (D12, D13). ADR-0083 *Modules, migrations and ejection* is superseded in part and gains a note.

## Engineering standards

Every phase passes before it is marked done:

1. `gofmt`, `go vet`, `go test -race`, `golangci-lint`, `govulncheck`, `gitleaks` clean in every module.
2. `apicheck`: every new public symbol in `api/*.txt`; every deprecated one still listed.
3. `refdocs -check`: every new public method has a doc comment and a runnable `Example`.
4. The v0.1 and v0.2 golden apps build and pass their tests against the branch's library, unchanged.
5. `/ops` and `/v1/auth` OpenAPI baselines unchanged for `--auth full`; a new baseline per profile.
6. Isolation tests: for every scope profile, a test that actor A in scope 1 gets 404 for a record in scope 2 on read, update, delete, list and search.
7. Benchmarks compared with the v0.2 baselines; no regression in start time or request latency outside budget.
8. Fuzz: `Scope.ValidID` and scope path parameter parsing join the fuzz targets.

## Not in v0.2.2

| Idea | Why not now |
|---|---|
| **External identity as a profile** (`--auth external`, tenancy from claims) | D14. `modules/jwt` already satisfies `gorbital.Authenticator` and `mobile-backend` proves it works wired by hand; item 27 keeps the seam open. The profile, `jwtscope`, the `JWT_*` configuration and the Auth0/Clerk guides are **v0.4**, and nothing here has to change for them |
| `orb add auth`, `orb add passkeys` on an existing app | Needs out-of-order migrations, a rollback story and its own ADR (D7). Also v0.4 |
| Pruning a disabled method's code from an ejected app | The layers are interlinked; pruning would not compile (D6). Needs `authhttp` split into per-method packages |
| Scope from a subdomain | A routing concern; it changes the middleware stack, not the contract |
| A second scope in one app (organisation inside a reseller) | The contract permits it; nothing in the guards or RLS does yet |
| `.orb` drift detection, `orb explain` | Depend on the manifest this release writes; they are the natural v0.4 |
| Retiring `shelfie`, `invoicing` and `admin-tool` | An editorial change to a dozen documentation pages. It must not ride along with the mechanical move of the apps (item 82) |
| Pruning `examples/minimal`, `examples/full-single`, `examples/full-multi` | They generate the CLI's templates and are byte-compared in CI. They are source, not examples, and stay in the library repository |
| The rest of `orb cyber` | Item 41 ships the five static rules that belong to this release's promise. Scanners, profiles and reports come later |
| `orb cyber`, `orb agent`, compliance profiles | Later, and only after the external security review |

## Risks

| Risk | Mitigation |
|---|---|
| A rename silently changes an authorisation decision | Phase 1 runs the entire existing membership suite through the compatibility layer before any vocabulary changes; the OpenAPI document of the golden multi-tenant app is byte-compared |
| A custom `ValidID` or `NotFoundCode` leaks whether a scope exists | The guard refuses malformed, unknown, deleted and forbidden with the same status and code; item 19 fuzzes it; item 68 reviews it |
| A hand-written `ScopeAuthorizer` gets the semantics wrong | `gorbital.ErrScopeNotFound` and the documented error contract; `byo-identity` is the worked reference; the generated isolation tests catch the common mistake |
| Profiles multiply into an untestable matrix | Nine legal combinations, enumerated in code (`LegalProfiles`), three byte-golden, all nine built and tested in CI (items 8, 58) |
| The manifest and the templates drift | A template path with no manifest entry is a build failure (item 51) |
| `--auth basic` ships an app full of code it does not call | Stated plainly in the docs and in `orb new`'s output, with the honest mitigation is item 40, which keeps the copied code patchable |
| The work does not fit one release | The spine is phases **1, 2, 3, 5** — the scope contract, organisations on it, the security line, and resource policies. Those four make the promise true. Phase 4 (CLI profiles) can slip to `v0.2.2.1`: the library would then offer the choices that `orb new` does not yet ask about. Phases 6 and 7 must ship with whatever ships, because a release whose documentation describes the old shape is worse than a later release |
| Moving the examples breaks the documentation build | The move (item 68) and the include resolution (items 75, 76) land in the same phase and the same pull request; `docscheck` failing is the gate |
| An example silently rots against the library | Nightly CI in the examples repository builds every app against gorbital `main` (item 70) |
